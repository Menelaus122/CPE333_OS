\section{โปรแกรมที่ใช้ทดลอง}
% =====================================================================

ตัวอย่างที่เลือกคือ\textbf{บัญชีเงินฝากร่วม}หนึ่งบัญชี ยอดเงินอยู่ในตัวแปร global \code{balance} (เริ่มต้น 1,000 บาท) ซึ่งตู้ ATM หลายตู้ใช้ร่วมกัน แต่ละตู้คือ thread หนึ่งตัว thread ครึ่งหนึ่งฝากเงินและอีกครึ่งหนึ่งถอนเงิน ครั้งละ 1 บาท จำนวนครั้งเท่ากัน \textbf{ยอดสุดท้ายที่ถูกต้องจึงต้องเป็น 1,000 บาทเสมอ} ต่างจากตัวอย่างในคาบเรียนที่เพิ่มค่าตัวนับทางเดียว ตัวอย่างนี้มีทั้งเพิ่มและลด ผลที่ผิดจึงเป็นได้ทั้งบวก (รายการถอนหาย) และลบ (รายการฝากหาย)

การฝากและถอนแก้ค่า \code{balance} ตรง ๆ โดยไม่มี lock ป้องกัน ซึ่งเป็นจุดที่ทำให้เกิด race condition

\begin{lstlisting}[caption={การฝากและถอนเงินที่ไม่มีการป้องกัน}]
void deposit_plain(void)
{
    balance = balance + AMOUNT;
}

void withdraw_plain(void)
{
    balance = balance - AMOUNT;
}
\end{lstlisting}

วิธีใช้คือ \code{./ps7 [threads] [tx\_per\_thread] [yield]} ถ้าระบุ 1 thread ตัวนั้นจะฝาก \code{tx} ครั้งแล้วจึงถอน \code{tx} ครั้ง ถ้าระบุเป็นเลขคู่ thread ครึ่งแรกฝาก ครึ่งหลังถอน ตัวละ \code{tx} ครั้ง \code{main()} สร้าง thread ทั้งหมดด้วย \code{pthread\_create()} ก่อนแล้วจึงรอด้วย \code{pthread\_join()} เพื่อให้ทุกตัวทำงานซ้อนกัน แต่ละ thread นับรายการที่ทำเสร็จไว้ในตัวแปร local ของตัวเอง ซึ่งไม่ได้ใช้ร่วมกันจึงถูกต้องเสมอ ใช้ยืนยันว่ารายการครบทุกรายการ

แต่ละรอบพิมพ์ผลหนึ่งบรรทัด \code{in} และ \code{out} คือจำนวนรายการฝากและถอนที่ทำจริง \code{expected} คือยอดที่ควรเป็น (1,000) \code{actual} คือค่าใน \code{balance} และ \code{diff} คือ \code{actual - expected} ท้ายบรรทัดเป็น \code{OK} เมื่อยอดถูกต้อง และ \code{RACE} เมื่อยอดผิด

คอมไพล์ด้วยคำสั่งตามใบงาน \code{gcc -o ps7 ps7.c -lpthread} โดยตั้งใจไม่ใส่ \code{-O} เพราะ \code{-O2} อาจรวบลูปทั้งลูปเหลือการบวกครั้งเดียว ทำให้ race condition แทบไม่ปรากฏ

\section{Task 3: บังคับ context switch}
% =====================================================================

เพิ่มโหมด \code{yield} ที่แยกการแก้ค่าเป็นสามขั้นตามตัวอย่างในใบงาน และเรียก \code{sched\_yield()} คั่นก่อนการเขียน (ไม่ใช้ \code{pthread\_yield()} เพราะ glibc 2.34 ขึ้นไปเลิกใช้แล้ว) จำนวนรายการลดเหลือ 100,000 ต่อ thread เพราะ \code{sched\_yield()} เป็น system call ทุกรอบ

\begin{lstlisting}[caption={การฝากและถอนที่บังคับ context switch ระหว่าง load กับ store}]
void deposit_yield(void)
{
    long reg = balance;         /* load   */
    reg = reg + AMOUNT;         /* modify */
    sched_yield();              /* force a context switch */
    balance = reg;              /* store  */
}

void withdraw_yield(void)
{
    long reg = balance;
    reg = reg - AMOUNT;
    sched_yield();
    balance = reg;
}
\end{lstlisting}

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{../result/screenshots/t06_task3_yield_multicore.png}
\caption{Task 3: คอมไพล์ใหม่แล้วรันโหมด yield บน CPU 22 ตัว 10 รอบ ผิดทุกรอบ}
\end{figure}

บน CPU 22 ตัว \textbf{ผิดทั้ง 10 รอบและไม่ซ้ำกัน} บวก 5 รอบ ลบ 5 รอบ ตั้งแต่ \mbox{-60,108} ถึง +30,997 บนเครื่องนี้ thread แต่ละตัวมักได้ CPU ของตัวเอง ถ้าไม่มี thread อื่นรออยู่ \code{sched\_yield()} จะไม่สลับจริง แต่ยังทำให้ช่วงระหว่าง load กับ store ยาวขึ้น thread บน CPU อื่นจึงเขียนแทรกได้ง่าย

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{../result/screenshots/t07_task3_yield_one_core.png}
\caption{Task 3: CPU ตัวเดียว 100,000 รายการต่อ thread โหมดปกติถูกทั้ง 10 รอบ โหมด yield ผิดทั้ง 10 รอบ}
\end{figure}

ภาพนี้เป็นการทดลองแบบควบคุมบน CPU ตัวเดียว ใช้จำนวน thread และจำนวนรายการเท่ากัน ต่างกันแค่การเรียก \code{sched\_yield()} ผลคือ\textbf{โหมดปกติถูกทั้ง 10 รอบ แต่โหมด yield ผิดทั้ง 10 รอบ} ยืนยันว่า context switch ที่เกิดระหว่าง load กับ store คือตัวที่ทำให้ค่าถูกเขียนทับ

ค่าที่ผิดในโหมด yield คือ +100,000 พอดี 5 รอบ และใกล้ \mbox{-100,000} อีก 5 รอบ เพราะ thread ทั้ง 4 ตัวผลัดกันทำทีละรายการ และแต่ละตัวอ่านค่าที่ตัวเองเพิ่งเขียนกลับมาเสมอ thread ฝากสองตัวจึงรวมกันเป็นตัวนับตัวเดียวที่เพิ่มรอบละ 1 ส่วน thread ถอนสองตัวลดรอบละ 1 สองฝั่งเขียนทับกันตลอด ยอดสุดท้ายจึงเป็นค่าของฝั่งที่เขียนคนสุดท้าย คือ 101,000 หรือ \mbox{-99,000}

\section{อภิปรายผลและสาเหตุของ race condition}
% =====================================================================

race condition ในโปรแกรมนี้เกิดจากเงื่อนไขสามข้อพร้อมกัน ข้อแรก \code{balance} เป็นตัวแปร global ที่ทุก thread ใช้ร่วมกัน ข้อสอง \code{balance = balance + AMOUNT} ไม่เป็น atomic เพราะเป็นสามคำสั่ง load, add และ store (ภาพ t05) และข้อสาม ไม่มี lock กันไม่ให้หลาย thread เข้า critical section นี้พร้อมกัน ผลคือ \textbf{lost update} ดังตัวอย่างในตาราง

\begin{table}[H]
\centering\small
\caption{ลำดับเหตุการณ์ที่ทำให้รายการถอนเงินหายไปหนึ่งรายการ}
\begin{tabular}{@{}p{1.2cm}p{4.9cm}p{4.9cm}p{4.0cm}@{}}
\toprule
\textbf{ลำดับ} & \textbf{thread A (ฝาก)} & \textbf{thread B (ถอน)} & \textbf{balance ในหน่วยความจำ} \\
\midrule
1 & load: \code{rax = 1000} & & 1000 \\
2 & add: \code{rax = 1001} & & 1000 \\
3 & & load: \code{rax = 1000} & 1000 \\
4 & & sub: \code{rax = 999} & 1000 \\
5 & & store: \code{balance = 999} & 999 \\
6 & store: \code{balance = 1001} & & 1001 \\
\bottomrule
\end{tabular}
\end{table}

ฝากหนึ่งครั้งและถอนหนึ่งครั้ง ยอดควรเป็น 1,000 แต่ได้ 1,001 เพราะ A เขียนค่าที่คำนวณจากข้อมูลเก่าทับผลของ B ถ้าขั้นที่ 5 กับ 6 สลับกัน ยอดจะเป็น 999 แทน ผลจึงขึ้นกับว่า thread ใด store คนสุดท้าย ขั้นที่ 3--5 เกิดได้ทั้งจาก B ทำงานพร้อมกันบน CPU อีกตัว (t03) และจาก A ถูกสลับออกหลังขั้นที่ 2 (t04 และ t07)

ลำดับการสลับถูกกำหนดโดย scheduler และขึ้นกับสิ่งที่โปรแกรมควบคุมไม่ได้ เช่น จังหวะของ timer interrupt, CPU ที่แต่ละ thread ได้ และงานอื่นในเครื่อง ผลจึงเปลี่ยนไปทุกครั้งที่รัน (non-deterministic) ส่วน \code{sched\_yield()} ไม่ได้สร้าง bug ขึ้นมาใหม่ เพียงบังคับให้ช่วงระหว่าง load กับ store ถูกแทรกแน่นอนทุกครั้ง แทนที่จะรอให้เกิดเองโดยบังเอิญ

โปรแกรมให้ผลถูกต้องเสมอเมื่อใช้ thread เดียว แต่เมื่อใช้หลาย thread ยอดเงินผิดและเปลี่ยนไปทุกครั้งที่รัน บน CPU หลายตัว race condition เกิดแทบทุกครั้งเพราะ thread ทำงานพร้อมกันจริง ส่วนบน CPU ตัวเดียวเกิดเฉพาะเมื่อ context switch ตกระหว่าง load กับ store ซึ่งไม่บ่อย และเมื่อบังคับ context switch ด้วย \code{sched\_yield()} ก็ผิดทุกครั้ง สาเหตุคือการอ่าน--แก้--เขียนตัวแปรที่ใช้ร่วมกันโดยไม่เป็น atomic และไม่มี mutual exclusion ข้อสังเกตสำคัญคือโปรแกรมที่มี race condition อาจรันผ่านได้หลายครั้ง (13 จาก 20 รอบใน t04) การรันแล้วได้ผลถูกจึงไม่ได้พิสูจน์ว่าโปรแกรมถูกต้อง ต้องป้องกัน critical section ด้วยกลไก synchronization เช่น mutex หรือคำสั่ง atomic
