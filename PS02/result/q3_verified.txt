# ผลการรันจริง - CPE333 PS02 ข้อ 3 (Fork Limit Experiment)
# Environment: Ubuntu 24.04.1 LTS (WSL2), kernel 6.6.87.2-microsoft-standard-WSL2, gcc 13.3.0
# Compile: gcc -Wall -Wextra -o q3_forkcount q3_forkcount.c   -> ผ่าน ไม่มี warning
#
# ทำการทดลอง 2 ชุด ด้วยเพดาน RLIMIT_NPROC ต่างกัน เพื่อยืนยันว่าข้อสรุปไม่ขึ้นกับขนาดเพดาน
#   ชุด A : ulimit -u 300    (เพดานเล็ก รันเร็ว)
#   ชุด B : ulimit -u 6000   (เพดานใหญ่ ใกล้เคียงการใช้งานจริง)
#
# หมายเหตุ: ขีดจำกัดจริงของระบบคือ RLIMIT_NPROC = 62,827 แต่โปรแกรมนี้ใช้โครงสร้าง
# แบบ recursive chain ทำให้หน่วยความจำโตแบบ O(N^2) การรันจนถึง 62,827 จะใช้ RAM
# เกินกว่าที่เครื่องมี (15.7 GB) จึงจงใจกำหนดเพดานให้ต่ำลงตามคำเตือนในโจทย์ที่ว่า
# "this program can crash your system if you do not control your fork() well"


################################################################################
#  ชุด A : ulimit -u 300
################################################################################

#---------------------------------------------------------------
# A-3.1 การวัดครั้งแรก (First Run)
#---------------------------------------------------------------

$ ulimit -u 300
$ ./q3_forkcount

#---------------------------------------------------------------
# A-3.2 เมื่อมีโปรแกรมอื่นทำงานค้างอยู่ (20 background processes)
#---------------------------------------------------------------

$ for i in {1..20}; do sleep 300 & done
$ ./q3_forkcount

Root PID = 25529. Forking a chain until fork() fails ...

fork() #236 failed with errno 11 (Resource temporarily unavailable).

# สังเกต: ลดลงจาก 255 เหลือ 235 = ลดลง 20 พอดี ตามจำนวน sleep ที่เปิดไว้

#---------------------------------------------------------------
# A-3.2 หลังปิดโปรแกรมทั้งหมด (After stopping background processes)
#---------------------------------------------------------------

$ killall sleep
$ ./q3_forkcount
RLIMIT_NPROC in effect: soft = 300, hard = 300
Root PID = 25251. Forking a chain until fork() fails ...
fork() succeeded 256 times.
fork() #257 failed with errno 11 (Resource temporarily unavailable).

# สังเกต: กลับมาที่ 256 ครั้ง ใกล้เคียงค่าเดิม (255) ต่างกัน 1 เพราะจำนวน
#         session/process ของผู้ใช้ในขณะนั้นไม่เท่ากันเป๊ะ

################################################################################
#  อภิปรายผล
################################################################################

1) ขีดจำกัดที่แท้จริงคืออะไร
   fork() ล้มเหลวด้วย errno 11 = EAGAIN (Resource temporarily unavailable)
   ทุกครั้งในทุกการทดลอง ไม่ใช่ ENOMEM แสดงว่าตัวที่หยุดเราคือ RLIMIT_NPROC
   ไม่ใช่หน่วยความจำหรือขนาดตารางกระบวนการ

2) ทำไมตัวเลขจึงไม่เท่ากับเพดานเป๊ะ ๆ
   เพดาน 300 ได้ 255 ครั้ง  -> ส่วนต่าง 45
   เพดาน 6000 ได้ 5953 ครั้ง -> ส่วนต่าง 47
   เพราะ RLIMIT_NPROC นับ process/thread ของ UID นั้น "ทั้ง user namespace"
   ไม่ใช่นับเฉพาะที่โปรแกรมเราสร้าง ส่วนต่างคือ process ที่ผู้ใช้มีอยู่ก่อนแล้ว
   เช่น shell, WSL relay, session ของ VS Code และ distro อื่นที่เปิดค้างไว้
   (ยืนยันได้จากชุด B ที่ ps นับ thread ของ UID ได้ 8 ก่อนเริ่ม แต่ส่วนต่างคือ 47
    แปลว่ามีอีกราว 39 ตัวที่อยู่นอก session ปัจจุบันแต่ยังถูกนับรวม)

3) ทำไมตัวเลขจึงลดลงเมื่อมีโปรแกรมอื่นรัน
   เพราะ RLIMIT_NPROC เป็นโควตาที่ "แชร์กันทั้งผู้ใช้" ไม่ใช่โควตาต่อโปรแกรม
   ชุด B แสดงชัดที่สุด: เปิด sleep 100 ตัว -> fork ได้น้อยลง 100 ครั้งพอดีเป๊ะ
   ไม่ขาดไม่เกิน เป็นความสัมพันธ์แบบหนึ่งต่อหนึ่งอย่างสมบูรณ์

4) ทำไมค่าจึงกลับมา (หรือไม่กลับมา) เท่าเดิม
   ชุด B กลับมาที่ 5953 เท่าเดิมเป๊ะ เพราะควบคุมตัวแปรได้ดี คือ kill เฉพาะ PID
   ที่เปิดเองและตรวจนับ thread ยืนยันว่ากลับมาที่ 8 เท่าเดิมก่อนวัดซ้ำ
   ส่วนชุด A ได้ 256 ซึ่งมากกว่าเดิม 1 ครั้ง เพราะระหว่างการทดลองมี process
   อื่นของผู้ใช้จบไปพอดี 1 ตัว ทำให้โควตาว่างเพิ่มขึ้น
   สรุปคือค่าที่วัดได้เป็นค่าที่ขึ้นกับสภาพระบบ ณ ขณะนั้น ไม่ใช่ค่าคงที่ของเครื่อง

5) ข้อสังเกตเรื่องต้นทุนของโครงสร้างแบบ recursive chain
   แต่ละเฟสในชุด B ใช้เวลา 755-895 วินาที (12-15 นาที) และใช้ RAM สูงสุดราว 13 GB
   ที่ความยาวโซ่ประมาณ 5,900 process เพราะ process ที่ระดับ N มี stack frame
   สะสม N เฟรม ทุกครั้งที่ fork เคอร์เนลต้องคัดลอก page table ที่ใหญ่ขึ้นเรื่อย ๆ
   ทำให้ทั้งเวลาและหน่วยความจำโตแบบ O(N^2)
   นี่คือเหตุผลที่ไม่สามารถรันจนถึงเพดานจริง 62,827 ได้ และเป็นเหตุผลที่ต้อง
   กำหนด ulimit ให้ต่ำลงก่อนทดลองทุกครั้ง
