\subsection{พื้นฐานที่ต้องเข้าใจก่อน: storage class คืออะไร}
% ---------------------------------------------------------------------

คำว่า \emph{storage class} ในภาษา C ไม่ได้บอกว่าตัวแปร ``เป็นชนิดอะไร''
แต่บอกว่าตัวแปรนั้น \textbf{ถูกเก็บไว้ที่ไหนในหน่วยความจำ} และ
\textbf{มีชีวิตอยู่นานแค่ไหน} คุณสมบัติที่ต้องแยกให้ออกมีสามเรื่อง

\begin{itemize}[leftmargin=*]
  \item \textbf{ขอบเขตการมองเห็น (scope)} คือบริเวณในโค้ดที่เรียกชื่อตัวแปรนี้ได้
  \item \textbf{อายุ (lifetime)} คือช่วงเวลาที่เนื้อที่ในหน่วยความจำของตัวแปรยังถูกจองไว้
  \item \textbf{การเชื่อมโยง (linkage)} คือไฟล์อื่นเห็นชื่อนี้ด้วยหรือไม่
\end{itemize}

หัวใจของข้อนี้คือ \textbf{scope กับ lifetime เป็นคนละเรื่องกัน} ตัวแปรหนึ่งตัว
มีขอบเขตแคบมาก (เห็นได้เฉพาะในบล็อกเดียว) แต่มีอายุยืนตลอดโปรแกรมได้
และนั่นคือสิ่งที่คำว่า \code{static} ทำ

อีกจุดที่ควรรู้คือคำว่า \code{auto} ในบรรทัด \code{auto int x = 3;} ของโจทย์
\textbf{ไม่ได้ทำอะไรเลย} เพราะตัวแปรที่ประกาศในบล็อกเป็น \code{auto}
อยู่แล้วโดยปริยาย เขียนหรือไม่เขียนผลลัพธ์เหมือนกันทุกประการ
(ในมาตรฐาน C23 คำนี้ถูกนำกลับมาใช้ในความหมายใหม่ คือให้คอมไพเลอร์เดาชนิดตัวแปรเอง
แต่ \code{gcc 13} ที่ใช้ในการทดลองนี้ตั้งต้นเป็น \code{-std=gnu17} จึงยังเป็นความหมายเดิม)

\subsection{Step 1: โปรแกรมที่มี \code{static} คอมไพล์แบบปกติ}
% ---------------------------------------------------------------------

\begin{lstlisting}[style=cstyle,caption={\code{src/q1\_static.c} คัดลอกจากโจทย์ทุกตัวอักษร}]
#include <stdio.h>
#include <stdlib.h>

void main()
{
    auto int x = 3;

    while (x > 0)
    {
        static int y = 5;
        y++;

        printf("The value of y is %d\n", y);
        printf("The address of y is %p\n\n", &y);

        x--;
    }
}
\end{lstlisting}

\subsubsection{อธิบายผล}

ผลที่ได้มีสองส่วนที่ต้องอธิบายแยกกัน คือ \emph{ค่า} กับ \emph{ที่อยู่}

\textbf{ค่าเป็น 6, 7, 8 ไม่ใช่ 6, 6, 6} \quad เพราะบรรทัด \code{static int y = 5;}
\textbf{ไม่ใช่คำสั่งที่ทำงานตอนวนลูป} แต่เป็นการบอกคอมไพเลอร์ให้จองเนื้อที่
ไว้ในส่วน \code{.data} ของไฟล์โปรแกรม พร้อมเขียนเลข \code{5} ลงไปในไฟล์ตั้งแต่
ตอนคอมไพล์ เมื่อโปรแกรมถูกโหลดขึ้นหน่วยความจำ ค่า \code{5} ก็ติดมากับส่วนนั้นเลย
การ ``กำหนดค่าเริ่มต้น'' จึงเกิดขึ้น \textbf{ครั้งเดียวก่อนโปรแกรมเริ่มทำงาน}
ไม่ได้เกิดซ้ำทุกรอบที่ผ่านบรรทัดนั้น พอวนลูปรอบที่สอง โปรแกรมข้ามบรรทัดประกาศ
ไปทำ \code{y++} ต่อจากค่าเดิมทันที ค่าจึงสะสมเป็น $5 \to 6 \to 7 \to 8$

\textbf{ที่อยู่เท่ากันทั้ง 3 รอบภายในการรันเดียว} \quad เป็นผลโดยตรงจากข้อแรก
คือมีตัวแปร \code{y} อยู่ \emph{ตัวเดียว} ตลอดโปรแกรม ไม่ได้ถูกสร้างใหม่ทุกรอบ
เมื่อมีตัวเดียวก็ย่อมมีที่อยู่เดียว

\textbf{แต่ที่อยู่เปลี่ยนทุกครั้งที่รันใหม่} \quad ทั้งที่เป็นไฟล์โปรแกรมเดียวกัน
สาเหตุคือ Ubuntu ตั้งค่า \code{gcc} ให้สร้าง \textbf{PIE (Position-Independent
Executable)} เป็นค่าตั้งต้น (ยืนยันได้จาก \code{gcc -v} ที่มี
\code{-{}-enable-default-pie}) ไฟล์แบบนี้ไม่ได้ผูกที่อยู่จริงไว้ในตัวไฟล์
แต่เก็บเป็น \emph{ระยะห่างจากจุดเริ่มของโปรแกรม} เอาไว้ เคอร์เนลจึงเลือก
\emph{ฐานที่โหลด} ใหม่แบบสุ่มได้ทุกครั้งที่รัน ซึ่งเป็นกลไก \textbf{ASLR}
(Address Space Layout Randomization) ที่เปิดอยู่ในเครื่องนี้
(\code{randomize\_va\_space} มีค่า 2) ที่อยู่ที่พิมพ์ออกมาจึงเป็น
``ฐานที่สุ่มได้ บวกกับ ระยะห่างคงที่'' หลักฐานอยู่ในหัวข้อ~\ref{sec:evidence}

\subsubsection{อธิบายผลและเปรียบเทียบกับ Step 1}

\textbf{ค่ากลายเป็น 6, 6, 6} \quad เพราะตอนนี้ \code{y} เป็นตัวแปรอัตโนมัติ
อายุของมันผูกกับ \emph{บล็อก} ไม่ใช่โปรแกรม ทุกครั้งที่วนเข้าบล็อกใหม่
ตัวแปรจะถูกสร้างใหม่และคำสั่ง \code{= 5} \emph{ทำงานจริงทุกรอบ}
(ต่างจาก \code{static} ที่เป็นการเขียนค่าลงไฟล์ตั้งแต่ตอนคอมไพล์)
พอบวกหนึ่งจึงได้ 6 เท่ากันทุกรอบ ค่าที่สะสมไว้รอบก่อนหายไปหมดตอนออกจากบล็อก

\textbf{ที่อยู่ยังเท่ากันทั้ง 3 รอบ แต่เป็นคนละเหตุผลกับ Step 1} \quad
จุดนี้เป็นจุดที่เข้าใจผิดกันบ่อยที่สุด ที่อยู่เท่ากันไม่ได้แปลว่าเป็นตัวแปรตัวเดิม
ความจริงคือคอมไพเลอร์จองสล็อตให้ \code{y} ไว้ใน \emph{stack frame ของ \code{main}}
ตั้งแต่ตอนเข้าฟังก์ชัน (เช่น ``ถอยจากยอด frame ไป 20 ไบต์'') และ frame ของ
\code{main} ไม่ได้ถูกทำลายระหว่างวนลูป การวนเข้าออกบล็อกจึงกลับมาใช้
\textbf{สล็อตเดิมซ้ำ} ทุกรอบ ที่อยู่จึงบังเอิญเท่ากัน แต่ \emph{เนื้อหา} ในสล็อตนั้น
ถูกเขียนทับด้วยเลข 5 ใหม่ทุกรอบ ซึ่งเห็นได้จากค่าที่ไม่สะสม
ถ้าย้ายบล็อกนั้นไปอยู่ในฟังก์ชันที่เรียกตัวเองซ้อนกัน (recursive)
ที่อยู่ก็จะต่างกันไปทุกครั้งทันที เพราะแต่ละครั้งได้ frame คนละอันบน stack

\textbf{ที่อยู่ยังเปลี่ยนทุกครั้งที่รันใหม่ และอยู่คนละย่านกับ Step 1} \quad
สังเกตว่าเลขของ Step 1 ขึ้นต้นด้วย \code{0x5...} แต่ของ Step 2 ขึ้นต้นด้วย
\code{0x7ff...} ซึ่งไม่ใช่ความบังเอิญ เลข \code{0x7ff...} คือย่านบนสุดของ
address space ที่ระบบปฏิบัติการวาง \emph{stack} ไว้ ส่วน \code{0x5...} คือย่านที่
เคอร์เนลใช้โหลดตัวโปรแกรมแบบ PIE หลักฐานว่าเลขนี้เป็น stack จริง
อยู่ในหัวข้อ~\ref{sec:evidence} ส่วนสาเหตุที่เปลี่ยนทุกครั้งก็คือ ASLR เช่นกัน
เพียงแต่เป็น \emph{การสุ่มตำแหน่ง stack} ซึ่งเป็นคนละกลไกกับการสุ่มฐานของ PIE

\textbf{(1) ค่าของ \code{y} ไม่เปลี่ยนเลยไม่ว่าจะคอมไพล์แบบไหน} \quad เพราะ
\code{-no-pie} เป็นเรื่องของ \emph{การจัดวางในหน่วยความจำ} ล้วน ๆ ไม่ได้เปลี่ยน
ความหมายของภาษา C แม้แต่นิดเดียว \code{static} ก็ยังคงเป็น \code{static}
ตัวแปรอัตโนมัติก็ยังเกิดใหม่ทุกรอบเหมือนเดิม

\textbf{(2) กรณี \code{static} ต่างชัดเจน} \quad ที่อยู่กลายเป็น \code{0x404018}
เท่ากันเป๊ะทั้งสามครั้ง เพราะ \code{-no-pie} สั่งให้ linker สร้างไฟล์ชนิด
\code{EXEC} ที่ \textbf{ผูกที่อยู่จริงไว้ตายตัวตั้งแต่ตอน link}
เคอร์เนลไม่มีทางเลือก ต้องโหลดโปรแกรมลงที่อยู่นั้นเป๊ะ ๆ เสมอ ตัวแปร \code{y}
ที่อยู่ในส่วน \code{.data} จึงมีที่อยู่เดิมทุกครั้ง ตรวจสอบได้ด้วย \code{nm}
ว่าเลข \code{0x404018} ที่โปรแกรมพิมพ์ออกมา คือเลขเดียวกับที่อยู่ในตาราง symbol
ของไฟล์ ไม่ได้ถูกกำหนดขึ้นตอนรันเลย

\textbf{(3) กรณีไม่มี \code{static} ไม่ต่างเลย} \quad ที่อยู่ยังเป็น \code{0x7ff...}
และยังสุ่มทุกครั้งเหมือนเดิม เพราะ \code{y} ตัวนี้อยู่บน \textbf{stack}
ซึ่ง \emph{ไม่ได้อยู่ในไฟล์โปรแกรม} เลย stack เป็นสิ่งที่เคอร์เนลสร้างให้
ตอนสร้าง process และตำแหน่งของมันถูกสุ่มโดยกลไก ASLR ของเคอร์เนล
ซึ่งเป็นคนละกลไกกับการสุ่มฐานของ PIE โดยสิ้นเชิง \code{-no-pie} จึงปิดได้
เฉพาะการสุ่มฐานของตัวโปรแกรม แต่ปิดการสุ่ม stack ไม่ได้
ถ้าอยากปิดการสุ่ม stack ด้วยต้องสั่งที่ระบบปฏิบัติการ เช่น \code{setarch -R}
หรือแก้ค่า \code{/proc/sys/kernel/randomize\_va\_space} ซึ่งได้ทดลองไว้แล้วในหัวข้อถัดไป

\textbf{ข้อสรุปของ Step 4} \quad \code{-no-pie} ไม่ได้ ``ปิด ASLR''
อย่างที่มักเข้าใจกัน มันแค่ทำให้ \emph{ตัวโปรแกรมและข้อมูลของโปรแกรม}
(\code{.text}, \code{.data}, \code{.bss}) มีที่อยู่ตายตัว ส่วน stack, heap
และไลบรารีที่โหลดตอนรัน ยังถูกสุ่มอยู่เหมือนเดิม

\subsection{หลักฐานยืนยันคำอธิบาย}
\label{sec:evidence}
% ---------------------------------------------------------------------

คำอธิบายทั้งหมดข้างต้นจะเป็นแค่การอ้างลอย ๆ ถ้าไม่มีการตรวจสอบจากอีกทาง
สคริปต์เก็บผลจึงมีหัวข้อ 4 ที่ไล่ตรวจสามเรื่อง คือ ตัวไฟล์เป็นชนิดอะไร
ตัวแปรอยู่ตรงไหนในไฟล์ และถ้าปิด ASLR แล้วผลจะเปลี่ยนไปอย่างไร

\textbf{หลักฐานที่ 1: ไฟล์ที่ได้เป็นคนละชนิดกันจริง}

\begin{lstlisting}[style=terminal,caption={ชนิดของไฟล์ ELF ทั้งสี่ (ตัด BuildID ออก)}]
$ file q1_static q1_auto q1_static_nopie q1_auto_nopie
q1_static:       ELF 64-bit LSB pie executable, x86-64, dynamically linked, ...
q1_auto:         ELF 64-bit LSB pie executable, x86-64, dynamically linked, ...
q1_static_nopie: ELF 64-bit LSB executable,     x86-64, dynamically linked, ...
q1_auto_nopie:   ELF 64-bit LSB executable,     x86-64, dynamically linked, ...

$ readelf -h q1_static       | grep -E 'Type|Entry'
  Type:                              DYN (Position-Independent Executable file)
  Entry point address:               0x1060          <- an offset, not a real address
$ readelf -h q1_static_nopie | grep -E 'Type|Entry'
  Type:                              EXEC (Executable file)
  Entry point address:               0x401050        <- a real, fixed address
\end{lstlisting}

\textbf{หลักฐานที่ 2: ตัวแปร \code{static} มีชื่อและที่อยู่อยู่ในไฟล์ ส่วนตัวแปรอัตโนมัติไม่มี}

\begin{lstlisting}[style=terminal,caption={ตาราง symbol และส่วน \code{.data}}]
$ nm q1_static_nopie | grep -i ' y'          # 'd' = a local symbol in .data
0000000000404018 d y.0                       <- exactly what the program printed

$ nm q1_static       | grep -i ' y'          # PIE: the same symbol, but as an offset
0000000000004010 d y.0

$ nm q1_auto_nopie   | grep -i ' y'          # nothing at all
(exit status = 1   -> 1 means grep found no symbol named y)

$ readelf -S q1_static_nopie | grep -A1 ' .data '
  [25] .data             PROGBITS         0000000000404008  00003008
       0000000000000014  0000000000000000  WA       0     0     8
\end{lstlisting}

บรรทัดแรกคือหลักฐานที่ตรงที่สุดของทั้งข้อ เลข \code{0x404018} ที่โปรแกรมพิมพ์
ออกมาตอนรัน คือเลขเดียวกับที่ \code{nm} อ่านได้จาก \emph{ตัวไฟล์} โดยไม่ต้องรันเลย
และมันตกอยู่ในช่วงของส่วน \code{.data} ที่เริ่มที่ \code{0x404008} พอดี
ส่วนชื่อ \code{y.0} ที่มีเลขต่อท้าย เป็นเพราะคอมไพเลอร์ต้องตั้งชื่อไม่ให้ชนกับ
\code{static} ตัวอื่นที่อาจชื่อ \code{y} เหมือนกันในฟังก์ชันอื่น
ในทางกลับกัน \code{q1\_auto\_nopie} ไม่มี symbol ชื่อ \code{y} เลย
เพราะตัวแปรอัตโนมัติไม่ใช่ ``ของ'' ที่อยู่ในไฟล์ แต่เป็นเพียงระยะห่างในโค้ด
ที่นำไปคำนวณกับ stack pointer ตอนรัน

\textbf{หลักฐานที่ 3: ปิด ASLR แล้วที่อยู่หยุดสุ่มจริง (กรณีควบคุม)}

\begin{lstlisting}[style=terminal,caption={รันไฟล์ PIE ชุดเดิมด้วย \code{setarch -R} ซึ่งปิดการสุ่ม address space}]
$ setarch -R ./q1_static | grep address        # run 1, 2, 3
The address of y is 0x555555558010
The address of y is 0x555555558010
The address of y is 0x555555558010

$ setarch -R ./q1_auto   | grep address        # run 1, 2, 3
The address of y is 0x7fffffffe290
The address of y is 0x7fffffffe290
The address of y is 0x7fffffffe290
\end{lstlisting}

ไฟล์เดียวกันกับที่เพิ่งให้ผลสุ่มไปเมื่อครู่ พอปิด ASLR กลับให้เลขเดิมทุกครั้ง
นี่คือหลักฐานว่าตัวการที่ทำให้ที่อยู่เปลี่ยนคือ ASLR ไม่ใช่ตัวภาษา C
และไม่ใช่ \code{static} ที่สำคัญคือ \code{q1\_auto} ที่คอมไพล์แบบ PIE
ก็หยุดสุ่มด้วย ทั้งที่ \code{-no-pie} ทำให้มันหยุดสุ่มไม่ได้
ยืนยันข้อสรุปของ Step 4 ว่าที่อยู่ของ stack ถูกคุมด้วย ASLR ของเคอร์เนล
ไม่ใช่ด้วยชนิดของไฟล์ ELF

\textbf{หลักฐานที่ 4: เลข \code{0x7ff...} เป็นที่อยู่บน stack จริง}

\begin{lstlisting}[style=terminal,caption={เทียบกับแผนที่หน่วยความจำจริง (ปิด ASLR ทั้งคู่เพื่อให้เทียบตัวเลขกันได้)}]
$ setarch -R ./q1_auto | grep address | head -1
The address of y is 0x7fffffffe290                     <- inside the range below

$ setarch -R bash -c 'grep "\[stack\]" /proc/self/maps'
7ffffffde000-7ffffffff000 rw-p 00000000 00:00 0                          [stack]

$ setarch -R ./q1_static | grep address | head -1
The address of y is 0x555555558010                     <- NOT inside that range
\end{lstlisting}

ที่อยู่ \code{0x7fffffffe290} ที่โปรแกรมพิมพ์ออกมา ตกอยู่ในช่วง
\code{0x7ffffffde000} ถึง \code{0x7ffffffff000} ที่เคอร์เนลระบุว่าเป็น
\code{[stack]} พอดี ในขณะที่ที่อยู่ของตัวแปร \code{static} อยู่คนละย่านโดยสิ้นเชิง

\begin{lstlisting}[style=terminal,caption={แยกส่วนที่สุ่มออกจากส่วนที่คงที่ (ระยะห่างของ \code{y} คือ \code{0x4010} จาก \code{nm})}]

ข้อสังเกตสองอย่าง หนึ่งคือฐานที่คำนวณได้ลงท้ายด้วย \code{000} ทุกครั้ง
เพราะเคอร์เนลสุ่มได้ทีละหน้า (page ละ 4096 ไบต์) ไม่ได้สุ่มทีละไบต์
สองคือไฟล์แบบ \code{-no-pie} มีฐานเป็นศูนย์ นั่นคือที่อยู่ที่พิมพ์ออกมา
เท่ากับที่อยู่ที่ระบุไว้ในไฟล์เป๊ะ ๆ ซึ่งเป็นนิยามของคำว่า ``ไม่ position-independent''

% ---------------------------------------------------------------------
\subsection{อภิปรายผล}
% ---------------------------------------------------------------------

\begin{itemize}[leftmargin=*]
  \item \textbf{\code{static} เปลี่ยน ``อายุ'' ไม่ได้เปลี่ยน ``ขอบเขต''}:
        เป็นบทเรียนหลักของข้อนี้ ตัวแปร \code{y} ในทั้งสองเวอร์ชันมีขอบเขต
        เท่ากันเป๊ะ คือเรียกใช้ได้เฉพาะในบล็อกของ \code{while} เท่านั้น
        โค้ดนอกบล็อกยังคอมไพล์ไม่ผ่านเหมือนกัน สิ่งที่ \code{static} เปลี่ยน
        คือย้ายตัวแปรจาก stack ไปอยู่ \code{.data} ทำให้อายุยืนตลอดโปรแกรม
        ผลคือได้ตัวแปรที่ ``จำค่าได้ระหว่างการเรียกแต่ละครั้ง แต่ไม่มีใครนอกบล็อก
        ไปยุ่งกับมันได้'' ซึ่งเป็นเหตุผลที่นิยมใช้ทำตัวนับหรือ cache ในฟังก์ชัน

  \item \textbf{การกำหนดค่าเริ่มต้นของ \code{static} เกิดตอนคอมไพล์ ไม่ใช่ตอนรัน}:
        เป็นสาเหตุที่ค่าออกมาเป็น 6, 7, 8 และเป็นเหตุผลที่มาตรฐาน C บังคับว่า
        ค่าเริ่มต้นของตัวแปร \code{static} ต้องเป็นค่าคงที่ที่รู้ตั้งแต่ตอนคอมไพล์
        (เขียน \code{static int y = rand();} ไม่ได้ แต่ \code{int y = rand();} ได้)
        ผลข้างเคียงอีกอย่างคือถ้าไม่ใส่ค่าเริ่มต้น ตัวแปร \code{static}
        จะได้ค่า \code{0} เสมอโดยไม่ต้องเสียเนื้อที่ในไฟล์ เพราะไปอยู่ในส่วน
        \code{.bss} ที่เคอร์เนลล้างเป็นศูนย์ให้ตอนโหลด ต่างจากตัวแปรอัตโนมัติ
        ที่ถ้าไม่ใส่ค่าเริ่มต้นจะได้ค่าขยะที่ค้างอยู่ใน stack

  \item \textbf{ที่อยู่ที่พิมพ์ออกมาเป็น virtual address ไม่ใช่ที่อยู่จริงบน RAM}:
        เห็นได้ชัดจากกรณี \code{-no-pie} ที่ทุก process ได้เลข \code{0x404018}
        เหมือนกันหมด ถ้ารันพร้อมกันสิบตัวก็ยังเป็นเลขนี้ทั้งสิบตัวและไม่ชนกัน
        เพราะแต่ละ process มี address space ของตัวเอง โดยมีหน่วย MMU
        กับตาราง page ของเคอร์เนลแปลงเลขนี้ไปเป็นที่อยู่จริงคนละที่กัน
        นี่คือภาพรูปธรรมของเรื่อง virtual memory ที่เรียนในทฤษฎี

  \item \textbf{เหตุผลที่ Linux รุ่นใหม่ทำ PIE เป็นค่าตั้งต้น คือความปลอดภัย}:
        การโจมตีแบบ buffer overflow ยุคใหม่ (เช่น return-to-libc หรือ ROP)
        ต้องรู้ที่อยู่ของโค้ดหรือข้อมูลที่จะกระโดดไปให้แม่นยำ การสุ่มฐานทุกครั้ง
        ที่รันทำให้ผู้โจมตีต้องเดา ซึ่งมักทำให้โปรแกรมพังไปเสียก่อน
        แลกมาด้วยราคาเล็กน้อยคือโค้ดต้องอ้างอิงแบบ relative
        จึงเป็นเหตุผลที่ \code{-no-pie} ยังมีอยู่ คือใช้ตอน debug
        ที่อยากให้ที่อยู่คงที่เพื่อเทียบผลได้ หรือใช้กับโค้ดเก่า
        ที่เขียนแบบผูกที่อยู่ตายตัว ไม่ใช่ตัวเลือกที่ควรใช้กับโปรแกรมจริง

  \item \textbf{ข้อควรระวังของ \code{static} ในโปรแกรมจริง}: เมื่อฟังก์ชันมี
        \code{static} อยู่ข้างใน ฟังก์ชันนั้นจะ ``จำอดีต'' ได้ ผลคือเรียกด้วย
        อาร์กิวเมนต์เดิมสองครั้งอาจได้ผลไม่เหมือนกัน ทำให้ทดสอบยากขึ้นมาก
        และที่ร้ายกว่านั้นคือถ้ามีหลาย thread เรียกฟังก์ชันเดียวกันพร้อมกัน
        ทุก thread จะใช้ตัวแปรตัวเดียวกัน เกิด race condition ทันที
        (ฟังก์ชันเก่าในไลบรารีมาตรฐานอย่าง \code{strtok} หรือ \code{ctime}
        มีปัญหานี้ จึงมีรุ่นลงท้ายด้วย \code{\_r} ที่ให้ผู้เรียกส่งที่เก็บสถานะมาเองแทน)

  \item \textbf{\code{void main()} ไม่ถูกต้องตามมาตรฐาน}: มาตรฐาน C กำหนดให้
        \code{main} คืนค่า \code{int} เพื่อส่ง exit status ให้ระบบปฏิบัติการ
        รายงานนี้คงโค้ดไว้ตามโจทย์และแนบ warning มาแสดงตามจริง แต่ในการใช้งานจริง
        ควรเขียนเป็น \code{int main(void)} และ \code{return 0;} เสมอ
        โดยเฉพาะเมื่อโปรแกรมจะถูกเรียกจากสคริปต์ที่ตรวจ exit status
\end{itemize}

\section{ข้อ 2: Extern Storage Class}

% ---------------------------------------------------------------------
\subsection{พื้นฐานที่ต้องเข้าใจก่อน: การประกาศ กับ การนิยาม}
% ---------------------------------------------------------------------

ข้อ 1 ว่าด้วย \emph{อายุ} ของตัวแปร ส่วนข้อนี้ว่าด้วย \emph{การเชื่อมโยง (linkage)}
คือเรื่องที่ว่าชื่อตัวแปรหนึ่งชื่อ ไฟล์อื่นเห็นด้วยหรือไม่ และหัวใจของมันคือ
การแยกให้ออกระหว่างสองคำที่คนมักใช้ปนกัน

\begin{itemize}[leftmargin=*]
  \item \textbf{การนิยาม (definition)} คือการสั่งให้ \emph{จองเนื้อที่จริง}
        ในหน่วยความจำ เช่น \code{int x = 20;} ที่เขียนนอกฟังก์ชัน
        ตัวแปรหนึ่งตัวมี definition ได้เพียงที่เดียวในทั้งโปรแกรม
  \item \textbf{การประกาศ (declaration)} คือการบอกคอมไพเลอร์เพียงว่า
        ``มีตัวแปรชื่อนี้ ชนิดนี้ อยู่ที่ไหนสักแห่ง เดี๋ยว linker ไปหามาให้''
        เช่น \code{extern int x;} ซึ่ง \emph{ไม่จองเนื้อที่ใด ๆ ทั้งสิ้น}
        และเขียนซ้ำกี่ที่ก็ได้
\end{itemize}

\begin{table}[H]
\centering\small
\caption{การนิยามกับการประกาศ ต่างกันตรงไหน}
\begin{tabular}{p{3.3cm}p{4.6cm}p{5.4cm}}
\toprule
\textbf{ประเด็น} & \textbf{\code{int x = 20;} (นอกฟังก์ชัน)} & \textbf{\code{extern int x;}} \\
\midrule
เรียกว่าอะไร & definition (นิยาม) & declaration (ประกาศ) \\
จองเนื้อที่ไหม & จอง 4 ไบต์ในส่วน \code{.data} & ไม่จองเลย \\
เขียนซ้ำได้ไหม & ได้ที่เดียวในทั้งโปรแกรม & กี่ที่ก็ได้ \\
ใครเป็นคนจัดการ & คอมไพเลอร์ & linker เป็นคนหาให้ตอนเชื่อมไฟล์ \\
ถ้าไม่มีเลยจะเกิดอะไร & \code{undefined reference} ตอน link & คอมไพล์ผ่าน แต่อาจหา definition ไม่เจอ \\
\bottomrule
\end{tabular}
\end{table}

จุดที่ต้องสังเกตในโค้ดของโจทย์คือ \code{extern int x;} ที่เขียนอยู่ \emph{ข้างใน}
\code{main()} และ \code{display()} นั้น อยู่ในไฟล์เดียวกันกับ \code{int x = 20;}
ที่เป็น definition อยู่แล้ว ทั้งสองบรรทัดจึงเป็นการเขียนซ้ำซ้อนที่
\textbf{ไม่มีผลอะไรเลย} เพราะตัวแปร global มองเห็นได้จากทุกฟังก์ชันในไฟล์อยู่แล้ว
ตั้งแต่บรรทัดที่นิยามมันลงไป ข้อนี้จึงน่าสนใจตรงที่ผลของการ \emph{ลบ} คำว่า
\code{extern} ออก ไม่ได้เป็นอย่างที่หลายคนคาดว่า ``main จะมองไม่เห็น \code{x}''
แต่กลับกลายเป็นอย่างอื่นไปเลย ซึ่งจะเห็นใน Step 2

% ---------------------------------------------------------------------
\subsection{Step 1: โปรแกรมที่มี \code{extern} ทั้งสองฟังก์ชัน}
% ---------------------------------------------------------------------

\begin{lstlisting}[style=cstyle,caption={\code{src/q2\_extern.c} คัดลอกจากโจทย์ทุกตัวอักษร}]
#include <stdio.h>
#include <stdlib.h>

int x = 20;

void display()
{
    extern int x;
    printf(" Display value of x: %d\n", x);
    printf(" Address of x (in display function): %p\n\n", &x);
}

void main()
{
    extern int x;
    printf(" Print value of x: %d\n", x);
    printf(" Address of x (in main function): %p\n\n", &x);

    display();
}
\end{lstlisting}

\subsubsection{อธิบายผล}

\textbf{ค่าเป็น 20 ทั้งสองที่} \quad เพราะทั้ง \code{main()} และ \code{display()}
กำลังพูดถึงตัวแปร \textbf{ตัวเดียวกัน} คือ \code{x} ที่นิยามไว้นอกฟังก์ชัน
คำว่า \code{extern} ในทั้งสองฟังก์ชันเป็นเพียงการยืนยันว่า ``ชื่อ \code{x} ที่ใช้ตรงนี้
หมายถึงตัวที่นิยามไว้ข้างนอก'' ซึ่งเป็นสิ่งที่คอมไพเลอร์เข้าใจอยู่แล้วโดยไม่ต้องบอก

\textbf{ที่อยู่ในสองฟังก์ชันตรงกันเป๊ะ} \quad นี่คือหลักฐานที่เข้มที่สุดว่ามีตัวแปร
เพียงตัวเดียวจริง ๆ ถ้าเป็นคนละตัวย่อมเป็นไปไม่ได้ที่ที่อยู่จะตรงกันทุกบิต
และตรงกันซ้ำแบบนี้ทั้งสามรอบ ข้อสังเกตนี้จะกลายเป็นเครื่องมือหลักในการอ่านผล
ของ Step 2 คือใช้ \emph{ที่อยู่} เป็นตัวบอกว่ากำลังดูตัวแปรตัวเดียวกันอยู่หรือเปล่า

\textbf{ที่อยู่เปลี่ยนทุกครั้งที่รันใหม่} \quad ด้วยเหตุผลเดียวกับข้อ 1 ทุกประการ
คือไฟล์เป็น PIE และเคอร์เนลสุ่มฐานที่โหลดใหม่ทุกครั้งตามกลไก ASLR
สังเกตว่าเลขลงท้าย \code{010} เหมือนกันทั้งสามรอบ เพราะระยะห่างของ \code{x}
จากฐานเป็นค่าคงที่ ส่วนที่เปลี่ยนคือฐานเท่านั้น

\subsubsection{อธิบายผลและเปรียบเทียบกับ Step 1}

\textbf{สิ่งที่เกิดขึ้นไม่ใช่ ``main มองไม่เห็น \code{x}'' แต่คือ ``main สร้าง
\code{x} ตัวใหม่''} \quad นี่คือหัวใจของข้อนี้ พอลบคำว่า \code{extern} ออก
บรรทัดนั้นเปลี่ยนจาก \emph{การประกาศ} ว่าจะใช้ตัวแปรข้างนอก กลายเป็น
\emph{การนิยาม} ตัวแปรอัตโนมัติตัวใหม่ชื่อ \code{x} ขึ้นมาใน \code{main()}
ผลคือชื่อ \code{x} ในขอบเขตของ \code{main} ถูกจับจองโดยตัวใหม่นี้
และ \textbf{บดบัง (shadow)} ตัวแปร global เดิมจนมองไม่เห็น
โปรแกรมยังคอมไพล์ผ่านและรันได้ตามปกติ เพราะในทางไวยากรณ์ไม่มีอะไรผิดเลย

\textbf{ค่าที่พิมพ์ออกมาเป็นค่าขยะ} \quad ตัวแปรใหม่นี้เป็นตัวแปรอัตโนมัติที่
ไม่ได้ใส่ค่าเริ่มต้น จึงได้ค่าที่ค้างอยู่ในสล็อตของ stack ตรงนั้น
ซึ่งตามมาตรฐาน C ถือเป็น \emph{undefined behavior} คอมไพเลอร์จับได้และเตือนไว้
ด้วย \code{-Wuninitialized} ตรงตำแหน่งบรรทัดที่ใช้งานพอดี ซึ่งเป็นเหตุผลที่ควร
คอมไพล์ด้วย \code{-Wall} เสมอ

\textbf{ค่าขยะที่ได้ไม่ได้สุ่มมั่ว แต่อธิบายได้} \quad สังเกตว่าค่าที่ออกมาวนอยู่
แถว 32765--32767 ซึ่งใกล้ค่าสูงสุดของ \code{short} พอดี เมื่อเทียบกับที่อยู่ของ
ตัวมันเองจะเห็นความสัมพันธ์ที่ตรงกันทุกรอบ

แต่ข้อนี้ให้ภาพที่คมกว่า เพราะเห็นผลทั้งสองแบบ \emph{ในโปรแกรมเดียวกัน}
คือ \code{q2\_noextern\_nopie} ตัวเดียว มีตัวแปรสองตัวที่ตอบสนองต่อ
\code{-no-pie} ไม่เหมือนกันเลย

\textbf{(1) ตัวแปร global ถูกตรึงที่อยู่ได้} \quad ด้วยเหตุผลเดียวกับตัวแปร
\code{static} ในข้อ 1 คือมันอยู่ในส่วน \code{.data} ซึ่งเป็นส่วนหนึ่งของไฟล์
เมื่อ linker ผูกที่อยู่จริงไว้ตั้งแต่ตอน link (ไฟล์ชนิด \code{EXEC})
เคอร์เนลก็ต้องโหลดลงที่เดิมเสมอ ที่น่าสนใจคือข้อนี้ให้ผลเหมือนข้อ 1 ทั้งที่
\code{static} กับ global เป็นคนละ storage class กัน ซึ่งยืนยันว่าสิ่งที่กำหนดว่า
ที่อยู่จะคงที่หรือไม่ ไม่ใช่ \emph{คีย์เวิร์ด} แต่คือ \emph{ตัวแปรไปอยู่ส่วนไหน
ของหน่วยความจำ}

\textbf{(2) ตัวแปรอัตโนมัติใน \code{main} ยังสุ่มเหมือนเดิม} \quad เพราะอยู่บน
stack ซึ่งเคอร์เนลเป็นคนสร้างและสุ่มตำแหน่งให้ตอนสร้าง process ไม่ได้อยู่ในไฟล์
\code{-no-pie} จึงไม่มีอำนาจอะไรกับมัน

\textbf{(3) ข้อควรระวังในการอ่านตัวเลข} \quad ที่อยู่ของ global ในไฟล์
\code{q2\_extern\_nopie} คือ \code{0x404018} แต่ในไฟล์
\code{q2\_noextern\_nopie} คือ \code{0x404020} ต่างกัน 8 ไบต์
ตัวเลขที่ไม่เท่ากันนี้ \emph{ไม่ได้} ขัดกับข้อสรุป เพราะเป็นคนละไฟล์ไบนารีกัน
(โค้ดต่างกัน linker จึงจัดวางต่างกันเล็กน้อย) สิ่งที่ข้อสรุปพูดถึงคือ
ที่อยู่ต้องคงที่เมื่อ \emph{รันไฟล์เดิมซ้ำ} ซึ่งเป็นจริงทั้งสองไฟล์

\textbf{(4) ค่าที่พิมพ์ไม่เปลี่ยน} \quad \code{-no-pie} เป็นเรื่องการจัดวาง
หน่วยความจำล้วน ๆ ไม่ได้แก้บั๊กการบดบังตัวแปรให้ และไม่ได้ทำให้ตัวแปร
ที่ไม่ได้กำหนดค่าเริ่มต้นกลายเป็นศูนย์

\subsection{หลักฐานยืนยันคำอธิบาย}
\label{sec:evidence2}
% ---------------------------------------------------------------------

\textbf{หลักฐานที่ 1: \code{x} เป็น symbol แบบ global จริง}

\begin{lstlisting}[style=terminal,caption={ตาราง symbol ของไฟล์ \code{-no-pie} ทั้งสอง}]
$ nm q2_extern_nopie   | grep -w x           # 'D' upper case = external linkage
0000000000404018 D x                         <- exactly what the program printed

$ nm q2_noextern_nopie | grep -w x           # the global x is still there, untouched
0000000000404020 D x                         <- the local x in main() has no symbol

$ readelf -s q2_extern_nopie | grep -w x
    21: 0000000000404018     4 OBJECT  GLOBAL DEFAULT   25 x
\end{lstlisting}

ตัวอักษร \code{D} \emph{ตัวใหญ่} คือจุดที่ต้องเทียบกับข้อ 1 ซึ่งได้
\code{d} \emph{ตัวเล็ก} สำหรับตัวแปร \code{static} ตัวใหญ่แปลว่า global
คือไฟล์อื่นเห็นและใช้ร่วมได้ ส่วนตัวเล็กแปลว่า local คือมีอยู่ในไฟล์นี้เท่านั้น
นี่คือ \emph{linkage} ที่จับต้องได้จริงในไฟล์ไบนารี ส่วน \code{readelf}
ยืนยันเพิ่มว่าเป็น \code{OBJECT} ขนาด 4 ไบต์ binding เป็น \code{GLOBAL}
และอยู่ใน section ที่ 25 ซึ่งก็คือ \code{.data} และที่สำคัญคือ
ไม่มี symbol ใดเลยสำหรับตัวแปร \code{x} ตัวใหม่ใน \code{main}
เพราะตัวแปรอัตโนมัติไม่ได้อยู่ในไฟล์

\textbf{หลักฐานที่ 2: คำว่า \code{extern} ในฟังก์ชันไม่สร้างโค้ดเครื่องเลยแม้แต่บิตเดียว}

ถ้าคำกล่าวที่ว่า ``\code{extern} ในฟังก์ชันเป็นการเขียนซ้ำซ้อน'' เป็นจริง
การลบ \emph{ทั้งบรรทัด} นั้นทิ้งไปเลยต้องได้โค้ดเครื่องที่เหมือนกันทุกไบต์
สคริปต์จึงสร้างไฟล์ \code{q2\_nodecl.c} ที่ไม่มีบรรทัดประกาศใน \code{main}
เลย แล้วเทียบ disassembly ของฟังก์ชัน \code{main} ระหว่างสองไฟล์

\begin{lstlisting}[style=terminal,caption={เทียบโค้ดเครื่องของ \code{main()} ระหว่างไฟล์ที่มีและไม่มีบรรทัด \code{extern int x;}}]

\code{404018} ซึ่งเป็นตัวแปร global โดยตรง ไม่มีการจองเนื้อที่บน stack ให้ \code{x}
เลยแม้แต่ไบต์เดียว (ไม่มีคำสั่ง \code{sub \$N,\%rsp} สำหรับตัวแปร)

\textbf{หลักฐานที่ 3: การประกาศไม่ใช่การนิยาม ถ้าไม่มีใครนิยาม linker จะฟ้อง}

\begin{lstlisting}[style=terminal,caption={ลบบรรทัด \code{int x = 20;} ทิ้ง เหลือแต่ \code{extern int x;} ในสองฟังก์ชัน}]

\emph{linker} ทั้งหมด เพราะ \code{extern int x;} เป็นการสัญญากับคอมไพเลอร์ว่า
``เดี๋ยวมีคนนิยามให้'' คอมไพเลอร์จึงปล่อยผ่านและทิ้งช่องว่างไว้ให้ linker เติม
พอถึงเวลาเชื่อมไฟล์แล้วหาไม่เจอจึงฟ้องครบทั้ง 4 จุดที่มีการอ้างถึง \code{x}
(สองจุดใน \code{display} และสองจุดใน \code{main})

\textbf{หลักฐานที่ 4: ปิด ASLR แล้วที่อยู่หยุดเปลี่ยน (กรณีควบคุม)}

\textbf{หลักฐานที่ 5: สิ่งที่ \code{extern} มีไว้ใช้จริง ๆ}

โจทย์ใช้ \code{extern} ในไฟล์เดียว ซึ่งไม่ใช่สถานการณ์ที่มันถูกออกแบบมาเพื่อแก้
การใช้งานจริงคือให้ไฟล์ \code{.c} หลายไฟล์ใช้ตัวแปรตัวเดียวกัน
จึงเขียนตัวอย่างสั้น ๆ สองไฟล์เพิ่มไว้เพื่อให้เห็นภาพ

เดียวกันเป๊ะ และการแก้ค่าจากไฟล์หนึ่งเห็นผลในอีกไฟล์ทันที

% ---------------------------------------------------------------------
\subsection{อภิปรายผล}
% ---------------------------------------------------------------------

\begin{itemize}[leftmargin=*]
  \item \textbf{\code{extern} เป็นคำสั่งที่พูดกับ linker ไม่ใช่กับ CPU}:
        ต่างจาก \code{static} ในข้อ 1 ที่มีผลจริงต่อการจัดวางหน่วยความจำ
        คำว่า \code{extern} ในโค้ดของโจทย์ไม่ได้ทำให้เกิดคำสั่งเครื่องเพิ่มขึ้น
        แม้แต่บิตเดียว (หลักฐานที่ 2) มันเป็นเพียงข้อมูลที่คอมไพเลอร์ใช้ตัดสินว่า
        ชื่อนี้หมายถึงอะไร แล้วฝากงานที่เหลือให้ linker ไปหา definition มาให้

  \item \textbf{บทเรียนที่แท้จริงของข้อนี้คือการบดบังตัวแปร (shadowing)}:
        โจทย์บอกให้ ``ลบคำว่า extern'' ซึ่งฟังดูเหมือนแค่เอาคำที่ไม่จำเป็นออก
        แต่ผลที่ได้กลับเป็นการสร้างตัวแปรใหม่ที่บังตัวเดิมทั้งดุ้น
        นี่เป็นบั๊กที่เจอบ่อยมากในโปรแกรมจริง เพราะคอมไพล์ผ่าน ไม่มี error
        และโปรแกรมยังรันได้ตามปกติ วิธีป้องกันคือเปิด \code{-Wshadow}
        เพิ่มจาก \code{-Wall -Wextra} ซึ่งจะเตือนทันทีที่ชื่อในบล็อกไปบังชื่อข้างนอก
        ในกรณีนี้ \code{-Wall} ช่วยจับได้อยู่แล้วโดยบังเอิญ ผ่านทาง
        \code{-Wuninitialized} แต่ถ้าโค้ดเขียนว่า \code{int x = 5;} แทน
        คำเตือนนั้นจะหายไปและบั๊กจะเงียบสนิท

  \item \textbf{ค่าขยะที่อธิบายได้ ไม่ได้แปลว่าพึ่งพาได้}: ตารางเทียบค่ากับที่อยู่
        แสดงว่าเลข 32765--32767 มีที่มาชัดเจน คือเศษของพอยน์เตอร์ที่ค้างอยู่ใน
        สล็อตนั้น แต่มาตรฐาน C ระบุว่าการอ่านตัวแปรอัตโนมัติที่ยังไม่กำหนดค่าเป็น
        undefined behavior ซึ่งแปลว่าคอมไพเลอร์มีสิทธิ์ทำอะไรก็ได้ รวมถึงตัดโค้ดทิ้ง
        หรือให้ผลต่างกันในแต่ละครั้งที่คอมไพล์ การอธิบายได้จึงมีค่าในแง่การเรียนรู้
        ว่าหน่วยความจำถูกใช้ซ้ำอย่างไร ไม่ใช่ในแง่การเขียนโปรแกรมจริง

  \item \textbf{ข้อ 1 กับข้อ 2 เป็นสองแกนที่ตั้งฉากกัน}: \code{static}
        ในข้อ 1 ทำให้ตัวแปร \emph{อายุยืนขึ้น} แต่ \emph{ปิด} การมองเห็นจากไฟล์อื่น
        ส่วน global กับ \code{extern} ในข้อ 2 \emph{เปิด} การมองเห็นให้กว้างที่สุด
        เห็นได้ชัดที่สุดจากตาราง symbol คือ \code{d y.0} ตัวเล็ก เทียบกับ
        \code{D x} ตัวใหญ่ ทั้งสองตัวอยู่ใน \code{.data} เหมือนกัน มีที่อยู่คงที่
        เมื่อคอมไพล์ด้วย \code{-no-pie} เหมือนกัน ต่างกันแค่ว่าใครเห็นชื่อมันได้บ้าง

  \item \textbf{ในโปรแกรมจริงไม่ควรเขียน \code{extern} ไว้ในไฟล์ \code{.c}}:
        วิธีที่ถูกต้องคือประกาศ \code{extern int x;} ไว้ในไฟล์ \code{.h}
        แล้วให้ทุกไฟล์ที่ต้องใช้ \code{\#include} เข้าไป ส่วน definition
        \code{int x = 20;} เขียนไว้ในไฟล์ \code{.c} เพียงไฟล์เดียว
        เหตุผลคือถ้าเขียนประกาศซ้ำ ๆ ในหลายไฟล์เอง วันที่ชนิดของตัวแปรเปลี่ยน
        จะต้องไล่แก้ทุกไฟล์ และถ้าแก้ไม่ครบ linker จะไม่ฟ้องด้วย เพราะมันจับคู่
        ด้วย \emph{ชื่อ} ไม่ได้ตรวจชนิด ซึ่งจะกลายเป็นบั๊กที่หายาก

  \item \textbf{ตัวแปร global ควรใช้เท่าที่จำเป็น}: ข้อนี้แสดงให้เห็นว่า
        ตัวแปร global ตัวเดียวถูกอ่านและแก้ได้จากทุกฟังก์ชันในโปรแกรม
        (ตัวอย่างสองไฟล์ในหลักฐานที่ 5 คือภาพชัด ๆ ที่ฟังก์ชันในอีกไฟล์
        แก้ค่าแล้วเห็นผลทันที) ซึ่งสะดวกแต่ทำให้ไล่หาสาเหตุของบั๊กยาก
        เพราะไม่มีทางรู้ว่าใครแก้ค่าไปบ้าง และเมื่อมีหลาย thread ก็เกิด
        race condition ได้เช่นเดียวกับตัวแปร \code{static} ในข้อ 1
        แนวทางที่ปลอดภัยกว่าคือส่งค่าผ่านพารามิเตอร์ของฟังก์ชัน
        หรือถ้าจำเป็นต้องมี global จริง ๆ ก็ประกาศเป็น \code{static}
        ที่ระดับไฟล์เพื่อจำกัดขอบเขตให้แคบที่สุดเท่าที่ทำได้
\end{itemize}

\subsubsection{อธิบายทีละหัวข้อตามที่โจทย์ถาม}

\textbf{(1) หัวข้อ \code{Address of Pointer}} \quad สองบรรทัดนี้คือ \code{\&a}
กับ \code{\&b} ซึ่งเป็นที่อยู่ของ \emph{ตัวแปรพอยน์เตอร์เอง} ไม่ใช่ของข้อมูลที่ถูกชี้
ทั้งคู่เป็นตัวแปรอัตโนมัติจึงอยู่บน stack ตรงกับที่ขึ้นต้นด้วย \code{0x7ff...}
และห่างกัน \code{0x278 - 0x270 = 8} ไบต์พอดี ซึ่งก็คือขนาดของพอยน์เตอร์
บนเครื่อง 64 บิต จุดที่ควรสังเกตคือ \code{b} เป็น \code{float *}
แต่ก็ยังกิน 8 ไบต์เท่ากับ \code{int *} เพราะขนาดของพอยน์เตอร์ขึ้นกับ
\emph{สถาปัตยกรรม} ไม่ได้ขึ้นกับชนิดของสิ่งที่มันชี้ไป

\textbf{(2) หัวข้อ \code{Effective Address}} \quad สองบรรทัดนี้คือ \code{a}
กับ \code{b} เฉย ๆ ซึ่งเป็น \emph{ค่าที่เก็บอยู่ข้างในตัวแปรพอยน์เตอร์}
คือที่อยู่ของก้อนข้อมูลที่มันชี้ไป แต่ ณ จุดนี้ยังไม่มีการ \code{malloc}
และไม่ได้กำหนดค่าเริ่มต้นให้ ค่าที่อยู่ข้างในจึงเป็นค่าที่ยังไม่กำหนด
(indeterminate) การอ่านมันคือ undefined behavior แบบเดียวกับตัวแปร \code{x}
ในข้อ 2 ผลที่ได้คือ \code{(nil)} ซึ่งเป็นวิธีที่ \code{printf} ใช้แสดง
พอยน์เตอร์ที่มีค่าเป็นศูนย์

ที่น่าสนใจคือ \textbf{ทำไมข้อ 2 ได้ค่าขยะ แต่ข้อนี้ได้ศูนย์} ทั้งที่เป็นตัวแปร
อัตโนมัติที่ไม่ได้กำหนดค่าเหมือนกัน คำอธิบายคือค่าที่ได้ขึ้นอยู่กับว่า
\emph{สล็อตนั้นเคยถูกใช้มาก่อนหรือยัง} ในข้อ 2 ตัวแปรไปตกในสล็อตที่โค้ดเริ่มต้น
โปรแกรมเคยใช้เก็บพอยน์เตอร์มาก่อน จึงเจอเศษค้างอยู่ ส่วนข้อนี้เฟรมของ
\code{main} กินลึกกว่าและไปตกในหน้าที่ยังไม่เคยถูกแตะเลย ซึ่งเคอร์เนล
รับประกันว่าหน้าใหม่ที่ยกให้ process จะถูกล้างเป็นศูนย์เสมอ (เพื่อไม่ให้ข้อมูล
ของ process อื่นรั่วออกมา) จึงอ่านได้ \code{0} ย้ำอีกครั้งว่า
\textbf{ไม่ใช่การรับประกันของภาษา} เป็นเพียงสิ่งที่บังเอิญเป็นในเครื่องนี้

\textbf{(3) หัวข้อ \code{After malloc Pointer a}} \quad หลังเรียก
\code{malloc(10 * sizeof(int))} คือขอ 40 ไบต์ ค่าใน \code{a} เปลี่ยนจากศูนย์
เป็นที่อยู่จริงบน heap (\code{0x610cfc37b4b0}) สังเกตว่าขึ้นต้นด้วย \code{0x5}
หรือ \code{0x6} ซึ่งเป็นย่านเดียวกับตัวโปรแกรม ไม่ใช่ \code{0x7ff...} แบบ stack
ส่วนอีกสองบรรทัดยืนยันกฎพื้นฐานสองข้อของอาร์เรย์

\begin{itemize}[leftmargin=*]
  \item \code{a} กับ \code{\&a[0]} ให้เลขเดียวกันเสมอ เพราะสมาชิกตัวแรก
        อยู่ต้นก้อนพอดี ไม่มีส่วนหัวอะไรมาคั่นในมุมมองของโปรแกรม
  \item \code{\&a[9]} ห่างจาก \code{a} เท่ากับ \code{0x4d4 - 0x4b0 = 0x24 = 36}
        ไบต์ ตรงกับ $9 \times \code{sizeof(int)} = 9 \times 4$ พอดี
        นั่นคือเลขดัชนีถูกคูณด้วยขนาดของชนิดข้อมูลให้อัตโนมัติ
\end{itemize}

\textbf{(4) หัวข้อ \code{Array c}} \quad อาร์เรย์ \code{c} ให้ผลรูปแบบเดียวกับ
\code{a} คือ \code{c} เท่ากับ \code{\&c[0]} และ \code{\&c[9]} ห่างออกไป 36 ไบต์
(\code{0x2a4 - 0x280 = 0x24}) แต่ \textbf{อยู่คนละย่านกันโดยสิ้นเชิง}
คือ \code{0x7ff...} เพราะ \code{c} เป็นอาร์เรย์อัตโนมัติที่คอมไพเลอร์จองไว้
ในเฟรมของ \code{main} ให้ตั้งแต่ตอนคอมไพล์ ไม่ต้องขอใครและไม่ต้องคืน
ต่างจาก \code{a} ที่ต้องขอตอนรันและต้อง \code{free} เอง
เมื่อเรียงที่อยู่ทั้งหมดบน stack จะเห็นว่าคอมไพเลอร์วางตัวแปรทั้งสามไว้ติดกัน
ตามลำดับที่ประกาศพอดี

\textbf{(5) หัวข้อ \code{After realloc Pointer a}} \quad \code{realloc}
ขยายก้อนเดิมจาก 40 ไบต์เป็น \code{1000 * sizeof(int)} คือ 4000 ไบต์
ในการรันครั้งนี้ที่อยู่ที่คืนมา \emph{เท่าเดิมทุกบิต} คือยังเป็น
\code{0x610cfc37b4b0} ซึ่งแปลว่าตัวจัดสรรขยายก้อนเดิมในที่เดิมได้สำเร็จ
โดยไม่ต้องย้ายข้อมูล เหตุผลว่าทำไมจึงขยายได้ และเงื่อนไขที่ทำให้ขยายไม่ได้
คือคำถามหลักของ Step 6 ซึ่งจะตอบในหัวข้อถัดไป
ส่วน \code{\&a[999]} ห่างจาก \code{a} เท่ากับ
\code{0xc44c - 0xb4b0 = 0xf9c = 3996} ไบต์ ตรงกับ $999 \times 4$ พอดี
ยืนยันว่าก้อนใหม่ใหญ่พอสำหรับ 1000 ตัวจริง

\textbf{(6) เลขไหนขยับ เลขไหนอยู่กับที่} \quad เทียบสองการรันจะเห็นว่า
\emph{ทุกเลขเปลี่ยนหมด} เพราะทั้ง stack และ heap ถูกสุ่มตำแหน่งด้วย ASLR
เหมือนที่พิสูจน์ไว้ในข้อ 1 และข้อ 2 แต่สิ่งที่ \emph{ไม่เปลี่ยน} คือ
\emph{ความสัมพันธ์} ระหว่างเลขเหล่านั้น ทั้งสองการรันได้ระยะห่างเท่ากันเป๊ะ
คือ 8 ไบต์ระหว่าง \code{\&a} กับ \code{\&b}, 36 ไบต์จาก \code{a} ถึง
\code{\&a[9]}, และเลข 12 บิตล่างของที่อยู่ heap ยังเป็น \code{4b0} เท่าเดิม
เพราะ ASLR สุ่มทีละหน้า ไม่ได้สุ่มตำแหน่งภายในหน้า

\subsubsection{ผลต่างจากเดิมหรือไม่ โดยเฉพาะที่อยู่ของ \code{a} เพราะอะไร}

\textbf{คำตอบคือ ที่อยู่ของ \code{a} หลัง \code{realloc} เปลี่ยนไป
ทั้งที่โค้ดส่วนของ \code{a} ไม่ได้ถูกแก้เลยแม้แต่ตัวอักษรเดียว}
และนี่คือประเด็นที่โจทย์ต้องการให้เห็น

เหตุผลอยู่ที่ \emph{ลำดับการจอง} ไม่ใช่ที่ตัวโค้ดของ \code{a}
เมื่อปิด ASLR แล้วเทียบตัวเลขจะเห็นภาพชัดมาก

\begin{itemize}[leftmargin=*]
  \item \textbf{กรณีเดิม (ไม่มี \code{b})}: ก้อนของ \code{a} ที่
        \code{0x...a2b0} เป็นก้อนสุดท้ายบน heap ด้านหลังมันเป็นพื้นที่ว่าง
        ที่ยังไม่มีใครใช้ (glibc เรียกว่า \emph{top chunk}) เมื่อสั่งขยายเป็น
        4000 ไบต์ ตัวจัดสรรจึงแค่ ``ดันเส้นแบ่ง'' ให้ก้อนเดิมยาวขึ้นได้เลย
        ไม่ต้องย้ายข้อมูล ที่อยู่จึงเท่าเดิม
  \item \textbf{กรณีใหม่ (มี \code{b})}: \code{malloc} ของ \code{b}
        ไปจองที่ \code{0x...a2e0} ซึ่งอยู่ \emph{ติดหลัง} ก้อนของ \code{a} พอดี
        พื้นที่ที่ \code{a} เคยขยายเข้าไปได้กลายเป็นของ \code{b} ไปแล้ว
        ตัวจัดสรรจึงขยายในที่เดิมไม่ได้ ต้องหาที่ใหม่ที่ใหญ่พอ
        คัดลอกข้อมูล 40 ไบต์เดิมไปไว้ที่ใหม่ แล้วปล่อยก้อนเก่าคืนเป็นพื้นที่ว่าง
        ที่ใหม่ที่ได้คือ \code{0x...a310} ซึ่งอยู่ถัดจากก้อนของ \code{b} ไปอีก
        48 ไบต์ คือที่ว่างถัดไปที่ใกล้ที่สุดนั่นเอง
\end{itemize}

\textbf{ส่วนเลขอื่นเปลี่ยนอย่างไรบ้าง} \quad หัวข้อ \code{Address of Pointer},
\code{Effective Address}, \code{After malloc Pointer a} และ \code{Array c}
ให้ผลรูปแบบเดิมทุกประการ เพราะโค้ดส่วนนั้นทำงานก่อนจะถึงบล็อกของ \code{b}
สิ่งเดียวที่เพิ่มเข้ามาคือหัวข้อ \code{After malloc Pointer b}
ซึ่งแสดงว่าตอนนี้ \code{b} ชี้ไปที่ heap จริงแล้ว (ไม่ใช่ \code{(nil)}
เหมือนตอนต้นโปรแกรม) และ \code{\&b[9]} ห่างจาก \code{b} เท่ากับ
\code{0x504 - 0x4e0 = 0x24 = 36} ไบต์ ซึ่งบังเอิญเท่ากับของ \code{a}
เพราะ \code{sizeof(float)} เท่ากับ \code{sizeof(int)} คือ 4 ไบต์เท่ากันพอดี

\textbf{ระยะห่าง 48 ไบต์บอกอะไร} \quad ทั้ง \code{b - a} และ
ระยะจาก \code{b} ไปยัง \code{a} ก้อนใหม่ เท่ากับ 48 ไบต์ ทั้งที่ขอไปแค่ 40 ไบต์
ส่วนต่าง 8 ไบต์คือ \emph{ส่วนหัวของก้อน} ที่ตัวจัดสรรใช้เก็บขนาดของก้อนเอาไว้
เพื่อให้ \code{free} รู้ว่าต้องคืนกี่ไบต์ โดยที่โปรแกรมไม่ต้องบอก
(สังเกตว่า \code{free(a)} รับแค่พอยน์เตอร์ ไม่ต้องบอกขนาด)
หลักฐานเรื่องนี้อยู่ในหัวข้อถัดไป

\subsection{หลักฐานยืนยันคำอธิบาย}
\label{sec:evidence3}
% ---------------------------------------------------------------------

คำอธิบายข้างต้นอ้างสามเรื่องที่ต้องพิสูจน์ คือ (ก) ที่อยู่แต่ละอันอยู่ในย่านที่ว่าไว้จริง
(ข) ส่วนต่าง 8 ไบต์เป็นส่วนหัวของก้อนจริง และ (ค) \code{realloc}
ตัดสินใจย้ายหรือไม่ย้ายตามที่ว่าไว้จริง โปรแกรม \code{q3\_regions.c}
ตรวจสอบทั้งสามเรื่องในการรันเดียว

\textbf{หลักฐานที่ 1: แต่ละที่อยู่อยู่ในย่านที่เคอร์เนลระบุชื่อไว้}

\begin{lstlisting}[style=terminal,caption={ที่อยู่จากโปรแกรม เทียบกับ \code{/proc/self/maps} ของ process ตัวเดียวกัน}]
== 1. one address from each region ==
&data_var    (a .data object) = 0x555555558010
heap_ptr     (from malloc)    = 0x5555555592a0
&stack_arr[0](a local array)  = 0x7fffffffe030
&heap_ptr    (the pointer)    = 0x7fffffffdfe8

555555558000-555555559000 rw-p 00003000 08:30 13511    /tmp/ps04_q3/q3_regions
555555559000-55555557a000 rw-p 00000000 00:00 0        [heap]
7ffffffde000-7ffffffff000 rw-p 00000000 00:00 0        [stack]
\end{lstlisting}

เทียบทีละบรรทัดจะเห็นว่าตรงกันหมด \code{0x555555558010} ตกอยู่ในช่วง
\code{...558000}--\code{...559000} ซึ่งเป็นส่วนที่เขียนได้ของตัวไฟล์โปรแกรมเอง
คือ \code{.data} ส่วน \code{0x5555555592a0} ที่ได้จาก \code{malloc}
ตกอยู่ในช่วงที่เคอร์เนลตั้งชื่อว่า \code{[heap]} ตรง ๆ
และทั้ง \code{\&heap\_ptr} กับ \code{\&stack\_arr[0]} ตกอยู่ในช่วง \code{[stack]}
ทั้งคู่ ยืนยันว่าตัวพอยน์เตอร์อยู่บน stack แต่ก้อนที่มันชี้ไปอยู่บน heap จริง

\textbf{หลักฐานที่ 2: ทำไมสองก้อนที่ขอ 40 ไบต์จึงห่างกัน 48 ไบต์}

\begin{lstlisting}[style=terminal,caption={ระยะห่างระหว่างก้อนที่ขอติดกัน สำหรับขนาดที่ขอต่าง ๆ}]
== 2. how far apart are consecutive malloc() blocks? ==
malloc( 1) -> 0x55555555a2e0
malloc( 8) -> 0x55555555a300   gap from previous block = 32 bytes
malloc(24) -> 0x55555555a320   gap from previous block = 32 bytes
malloc(25) -> 0x55555555a340   gap from previous block = 32 bytes
malloc(40) -> 0x55555555a370   gap from previous block = 48 bytes
malloc(40) -> 0x55555555a3a0   gap from previous block = 48 bytes
\end{lstlisting}

ตัวเลขชุดนี้อธิบายได้ด้วยกฎง่าย ๆ ข้อเดียวคือ ก้อนจริงที่ตัวจัดสรรใช้
เท่ากับ ``ขนาดที่ขอ บวก 8 ไบต์สำหรับส่วนหัว แล้วปัดขึ้นให้ลงตัว 16''
โดยมีขนาดขั้นต่ำ 32 ไบต์ ลองแทนค่าดู ขอ 24 ได้ $24+8=32$ ลงตัว 16 พอดี
จึงเป็น 32 ขอ 25 ได้ $25+8=33$ ปัดขึ้นเป็น 48 ขอ 40 ได้ $40+8=48$ ลงตัวพอดี
จึงเป็น 48 ตรงกับที่วัดได้ทุกบรรทัด และตรงกับระยะ 48 ไบต์ระหว่าง \code{a}
กับ \code{b} ในโปรแกรมของโจทย์ นี่คือ \emph{ต้นทุนแฝง} ของ \code{malloc}
ที่โปรแกรมมองไม่เห็น คือขอ 40 ได้ใช้ 40 แต่กินจริง 48

\textbf{หลักฐานที่ 3: เงื่อนไขที่ \code{realloc} ย้ายหรือไม่ย้าย}

\begin{lstlisting}[style=terminal,caption={การทดลองแบบมีกรณีควบคุม ต่างกันแค่มีก้อนอื่นมาขวางหรือไม่}]

case B  a block behind it  : 0x55555555a3d0 -> 0x55555555a430   MOVED
\end{lstlisting}

สองกรณีนี้ต่างกันเพียงจุดเดียวคือ กรณี B มีการ \code{malloc} ก้อนอื่นคั่นไว้
ก่อนเรียก \code{realloc} ผลที่ได้คือกรณี A ได้ที่อยู่เดิม ส่วนกรณี B ถูกย้าย
ซึ่งเป็นพฤติกรรมเดียวกับที่เห็นในโปรแกรมของโจทย์ทุกประการ
ยืนยันว่าคำอธิบายเรื่อง ``ก้อนของ \code{b} ไปขวางทางขยายของ \code{a}''
ไม่ใช่การเดา แต่ทำซ้ำได้ในโปรแกรมที่คุมตัวแปรอื่นไว้หมดแล้ว

\subsection{อภิปรายผล}
% ---------------------------------------------------------------------

\begin{itemize}[leftmargin=*]
  \item \textbf{stack กับ heap ต่างกันที่ ``ใครเป็นคนตัดสินใจ''}: อาร์เรย์
        \code{c} กับก้อนของ \code{a} เก็บข้อมูลชนิดเดียวกันจำนวนเท่ากัน
        และใช้งานด้วยไวยากรณ์ \code{[i]} เหมือนกันทุกประการ
        แต่ \code{c} คอมไพเลอร์ตัดสินใจให้ตั้งแต่ตอนคอมไพล์ว่าต้องใหญ่เท่าไร
        และคืนให้อัตโนมัติเมื่อออกจากฟังก์ชัน ส่วนก้อนของ \code{a}
        โปรแกรมตัดสินใจเองตอนรัน จะขอเท่าไรก็ได้ (แม้แต่ค่าที่เพิ่งรับจากผู้ใช้)
        จะขยายทีหลังก็ได้ แต่แลกมาด้วยความรับผิดชอบที่ต้องคืนเอง
        ข้อดีอีกอย่างของ heap คือก้อนที่ขอไม่หายไปเมื่อฟังก์ชันจบ
        จึงเป็นวิธีเดียวที่ฟังก์ชันจะคืนอาร์เรย์ที่สร้างขึ้นเองกลับไปให้ผู้เรียกได้

  \item \textbf{\code{realloc} อาจย้ายที่ ดังนั้นห้ามเก็บที่อยู่เก่าไว้ใช้ต่อ}:
        นี่คือบทเรียนที่ใช้ได้จริงที่สุดของข้อนี้ ผลการทดลองแสดงว่า
        \emph{โค้ดชุดเดียวกัน} ให้ผลได้ทั้งสองแบบ ขึ้นกับสิ่งที่เกิดขึ้นรอบ ๆ
        ซึ่งโปรแกรมเมอร์ควบคุมไม่ได้ ถ้ามีพอยน์เตอร์ตัวอื่นชี้เข้าไปในก้อนนั้นอยู่
        หลัง \code{realloc} มันจะกลายเป็น dangling pointer ทันทีโดยไม่มีสัญญาณเตือน
        คอมไพเลอร์รุ่นใหม่ช่วยจับให้ได้บ้างด้วย \code{-Wuse-after-free}
        ซึ่งเจอจริงตอนเขียนโปรแกรมตรวจสอบของข้อนี้ จึงต้องแก้ให้เก็บที่อยู่เก่า
        เป็นตัวเลขแทนการเก็บเป็นพอยน์เตอร์

  \item \textbf{รูปแบบ \code{a = realloc(a, ...)} ที่โจทย์ใช้เป็นรูปแบบที่มีบั๊ก}:
        ถ้า \code{realloc} ทำงานไม่สำเร็จ มันจะคืน \code{NULL}
        \emph{โดยที่ก้อนเดิมยังอยู่ครบ} การเขียนทับ \code{a} ด้วย \code{NULL}
        จึงทำให้ที่อยู่ของก้อนเดิมหายไปตลอดกาล คืนก็ไม่ได้ ใช้ก็ไม่ได้
        กลายเป็น memory leak ทันที วิธีที่ถูกต้องคือรับค่าไว้ในตัวแปรชั่วคราวก่อน
        แล้วค่อยตรวจว่าไม่ใช่ \code{NULL} จึงย้ายมาใส่ \code{a}
        ในโปรแกรมของโจทย์ยังไม่เห็นปัญหาเพราะขอแค่ 4000 ไบต์ซึ่งไม่มีวันล้มเหลว
        แต่รูปแบบนี้ไม่ควรนำไปใช้ต่อ

  \item \textbf{\code{free} ต้องคู่กับ \code{malloc} เสมอ และการทดลองนี้แสดงให้เห็นทั้งสองแบบ}:
        ใน Step 1 บรรทัด \code{free(b)} ถูกคอมเมนต์ไว้ ซึ่ง \emph{ถูกต้องแล้ว}
        เพราะ \code{b} ยังไม่เคยถูก \code{malloc} เลย ถ้าเผลอเปิดคอมเมนต์
        เฉพาะบรรทัด \code{free(b)} โดยไม่เปิดบล็อก \code{malloc}
        โปรแกรมจะพยายามคืนพอยน์เตอร์ที่ไม่เคยขอ ซึ่งเป็น undefined behavior
        (ถ้าค่าเป็น \code{NULL} พอดีจะรอด เพราะมาตรฐานกำหนดให้ \code{free(NULL)}
        ไม่ทำอะไร แต่ถ้าเป็นค่าขยะจะพังทันที) ในทางกลับกัน ถ้าเปิดเฉพาะบล็อก
        \code{malloc} โดยลืมเปิด \code{free(b)} ก็จะรั่ว 40 ไบต์
        โจทย์จึงสั่งให้เปิดทั้งสองที่พร้อมกัน

  \item \textbf{ค่า \code{(nil)} ที่เห็นเป็นความบังเอิญ ไม่ใช่การรับประกัน}:
        เทียบกับข้อ 2 ที่ตัวแปรอัตโนมัติแบบเดียวกันให้ค่าขยะที่ไม่เป็นศูนย์
        จะเห็นว่าผลขึ้นกับว่าสล็อตนั้นเคยถูกใช้มาก่อนหรือไม่ล้วน ๆ
        พอยน์เตอร์ที่ยังไม่ได้กำหนดค่าจึงอันตรายกว่าตัวแปรธรรมดามาก
        เพราะถ้าเผลอ dereference โดยที่ค่าเป็นขยะ จะไปเขียนทับหน่วยความจำ
        ที่ไหนก็ไม่รู้ วิธีป้องกันที่ง่ายที่สุดคือเขียน \code{int *a = NULL;}
        ตั้งแต่ตอนประกาศเสมอ

  \item \textbf{\code{malloc} ไม่ใช่ system call และไม่ได้คุยกับเคอร์เนลทุกครั้ง}:
        จาก \code{/proc/self/maps} จะเห็นว่า \code{[heap]} มีขนาดถึง
        \code{0x21000} คือ 132 KB ทั้งที่โปรแกรมขอไปไม่กี่สิบไบต์
        เพราะ \code{malloc} เป็นฟังก์ชันในไลบรารี \code{glibc}
        ที่ขอหน่วยความจำก้อนใหญ่จากเคอร์เนลมาเก็บไว้ก่อน แล้วแบ่งย่อยให้
        โปรแกรมเองภายใน การเรียก \code{malloc} ส่วนใหญ่จึงไม่ต้องเข้าเคอร์เนลเลย
        ซึ่งเร็วกว่ามาก และเป็นเหตุผลที่ตัวจัดสรรต้องเก็บส่วนหัว 8 ไบต์
        ไว้กับทุกก้อน เพราะมันต้องจดจำเองว่าก้อนไหนใหญ่เท่าไรและว่างหรือไม่
\end{itemize}
