\section{คำสั่ง Linux สำหรับจัดการและเฝ้าดู process และ job}
% =====================================================================

ข้อนี้เป็นการศึกษาคำสั่งพื้นฐานสามกลุ่มที่ใช้ทำงานกับ process บนลินุกซ์ คือ
กลุ่ม \emph{เฝ้าดู} (\code{ps}, \code{top}) กลุ่ม \emph{ปรับลำดับความสำคัญ}
(\code{nice}, \code{renice}) และกลุ่ม \emph{ส่งสัญญาณควบคุม}
(\code{kill}, \code{pkill}, \code{killall}) โดยทุกหัวข้อมีการทดลองจริงประกอบ
ไม่ได้อธิบายจากคู่มือเพียงอย่างเดียว

% ---------------------------------------------------------------------
\subsection{ความแตกต่างระหว่างคำสั่ง \code{top} และ \code{ps}}
% ---------------------------------------------------------------------

\subsubsection{หลักการของทั้งสองคำสั่ง}

ทั้ง \code{ps} และ \code{top} อ่านข้อมูลจากแหล่งเดียวกันคือระบบไฟล์เสมือน
\code{/proc} ซึ่งเคอร์เนลเปิดให้อ่านสถานะของทุก process ได้
ความต่างจึงไม่ได้อยู่ที่ \emph{ข้อมูล} แต่อยู่ที่ \emph{วิธีนำเสนอข้อมูล}

\begin{itemize}[leftmargin=*]
  \item \code{ps} (process status) เป็นคำสั่งแบบ \textbf{one-shot snapshot}
        คือเดินอ่าน \code{/proc} หนึ่งรอบ พิมพ์ผลออกมา แล้วจบการทำงานทันที
        ได้ภาพนิ่งของระบบ ณ วินาทีที่สั่ง
  \item \code{top} (table of processes) เป็นโปรแกรมแบบ \textbf{interactive}
        ที่วนอ่าน \code{/proc} ซ้ำทุก ๆ ช่วงเวลา (ค่าตั้งต้น 3 วินาที)
        แล้ววาดหน้าจอใหม่ทับของเดิม จนกว่าผู้ใช้จะกด \code{q} เพื่อออก
        ได้ภาพเคลื่อนไหวของระบบตามเวลาจริง
\end{itemize}

  & ไม่เหมาะ เพราะผลลัพธ์เป็นหน้าจอ ต้องสั่ง \code{top -b -n 1} (batch mode) จึงจะนำไปใช้ต่อได้ \\

  & แทบไม่มี เพราะจบทันที (วัดได้ 0.00 วินาที)

\subsubsection{ผลการทดลอง: คำสั่ง \code{ps}}

เมื่อสั่ง \code{ps} เปล่า ๆ จะเห็นเฉพาะ process ที่เป็นของผู้ใช้คนเดียวกัน
และผูกอยู่กับ terminal (\code{pts/4}) เดียวกันเท่านั้น ไม่ใช่ทั้งระบบ

\begin{lstlisting}[style=terminal,caption={\code{ps} แบบไม่ใส่ option}]
$ ps
    PID TTY          TIME CMD
   5688 pts/4    00:00:00 bash
   5689 pts/4    00:00:00 bash
   5691 pts/4    00:00:00 sed
   5744 pts/4    00:00:00 ps
\end{lstlisting}

การจะเห็นทั้งระบบต้องใส่ option เพิ่ม ซึ่ง \code{ps} รองรับไวยากรณ์สองแบบ
คือแบบ BSD (\code{aux} ไม่มีขีดนำหน้า) และแบบ UNIX (\code{-ef} มีขีดนำหน้า)

\begin{lstlisting}[style=terminal,caption={\code{ps aux} -- ไวยากรณ์แบบ BSD}]
$ ps aux | head -8

root           1  0.0  0.0  21792 12084 ?        Ss   12:03   0:01 /sbin/init
root           2  0.0  0.0   3072  1760 ?        Sl   12:03   0:00 /init
root           7  0.0  0.0   3132  2112 ?        Sl   12:03   0:07 plan9 --control-socket 7 ...
root          56  0.0  0.0  66828 14196 ?        S<s  12:03   0:01 /usr/lib/systemd/systemd-journald

ความต่างที่ใช้งานจริงคือ \code{ps aux} ให้ \code{\%CPU}, \code{\%MEM} และ
\code{STAT} มาด้วย ส่วน \code{ps -ef} ให้คอลัมน์ \code{PPID} ซึ่งจำเป็นเวลาต้อง
ไล่ความสัมพันธ์พ่อลูกของ process (เช่นที่ใช้ตรวจ orphan process ใน PS02)

จุดแข็งที่สุดของ \code{ps} คือ option \code{-o} ที่ให้เลือกคอลัมน์เองได้
และ \code{--sort} ที่เรียงลำดับได้ ในการทดลองนี้ได้สั่งโปรแกรม \code{q1\_burn}
ให้กิน CPU ค้างไว้เป็นเป้าก่อน แล้วจึงเรียงตาม \code{\%CPU} จากมากไปน้อย

\begin{lstlisting}[style=terminal,caption={\code{ps -eo ... --sort=-\%cpu} เลือกคอลัมน์เองและเรียงลำดับ}]
$ taskset -c 0 ./q1_burn 30 MONITOR_ME &      # a CPU-hungry process to watch
$ ps -eo pid,ppid,ni,pri,stat,%cpu,%mem,etime,comm --sort=-%cpu | head -6
    PID    PPID  NI PRI STAT %CPU %MEM     ELAPSED COMMAND
   5749    5689   0  19 R+    109  0.0       00:02 q1_burn
      7       2   0  19 Sl    0.0  0.0    02:51:41 init
    102       1   0  19 Ss    0.0  0.0    02:51:41 systemd-udevd
   5683     102   0  19 S     0.0  0.0       01:46 (udev-worker)
      1       0   0  19 Ss    0.0  0.0    02:51:42 systemd
\end{lstlisting}

และเนื่องจาก \code{ps} จบการทำงานทันที จึงวัดเวลาได้ว่าใช้เวลาน้อยกว่า 0.01 วินาที

\subsubsection{อภิปรายผล}

\begin{itemize}[leftmargin=*]
  \item \textbf{ต่างกันที่ \emph{มิติเวลา} เป็นหลัก}:
        \code{ps} ตอบคำถามว่า ``ณ วินาทีนี้มีอะไรอยู่ในระบบบ้าง'' ส่วน \code{top}
        ตอบคำถามว่า ``ตอนนี้ระบบกำลังทำอะไรอยู่'' การทดลองยืนยันข้อนี้ชัดเจน
        คือ \code{ps aux} ใช้เวลา \code{0.00} วินาทีแล้วจบ ในขณะที่ \code{top}
        ต้องถูกบังคับด้วย \code{-n 1} ถึงจะยอมจบ ถ้าไม่ใส่จะรันค้างไปเรื่อย ๆ

  \item \textbf{ค่า \code{\%CPU} ของสองคำสั่งนี้ ``ไม่ใช่ค่าเดียวกัน''}:
        เป็นจุดที่ทำให้สับสนบ่อยที่สุด ค่าของ \code{ps} คือ
        \emph{เวลา CPU ที่ใช้ไปทั้งหมด หารด้วยอายุของ process} จึงเป็นค่าเฉลี่ย
        ย้อนหลังตลอดอายุ ส่วนค่าของ \code{top} คิดจาก
        \emph{ส่วนต่างของเวลา CPU ระหว่างสองรอบรีเฟรชล่าสุด} จึงเป็นค่าปัจจุบัน
        ผลที่ตามมาคือ process ที่เคยกิน CPU หนักเมื่อชั่วโมงที่แล้วแต่ตอนนี้
        หลับอยู่ จะยังมี \code{\%CPU} สูงใน \code{ps} แต่เป็น \code{0.0} ใน
        \code{top} ในการทดลองนี้ \code{ps} รายงาน \code{109} ให้ \code{q1\_burn}
        ที่เพิ่งเกิดได้ 2 วินาที (คอลัมน์ \code{ELAPSED} แสดง \code{00:02}
        ซึ่งปัดเป็นวินาทีเต็ม จึงหารแล้วเกิน 100 ได้เล็กน้อย) ขณะที่ \code{top}
        รายงาน \code{100.0} ตรงตามความเป็นจริง

  \item \textbf{\code{top} ให้ภาพรวมของ ``ระบบ'' ส่วน \code{ps} ให้ภาพของ ``process''}:
        ข้อมูล load average, จำนวน zombie, \code{\%Cpu(s)} แยก us/sy/ni/id/wa
        และหน่วยความจำรวม มีเฉพาะใน \code{top} ถ้าจะเอาข้อมูลชุดนี้จาก \code{ps}
        ต้องไปอ่านจาก \code{/proc/loadavg} และ \code{/proc/meminfo} เอง

  \item \textbf{\code{ps} ชนะขาดเรื่องการนำผลไปใช้ต่อ}:
        เพราะผลลัพธ์เป็นข้อความบรรทัดต่อบรรทัดที่ต่อ pipe ได้ทันที
        และเลือกคอลัมน์เองได้ด้วย \code{-o} ดังที่ใช้ในการทดลองข้อ 1.2 และ 1.3
        ตลอดทั้งรายงานนี้ ส่วน \code{top} ต้องพึ่ง \code{-b} เพื่อบังคับให้พิมพ์
        เป็นข้อความธรรมดา ซึ่งก็ยังต้อง \code{grep} ตัดส่วนหัวออกอยู่ดี

  \item \textbf{\code{top} ทำสิ่งที่ \code{ps} ทำไม่ได้ คือ ``สั่งการ''}:
        \code{ps} เป็นคำสั่งอ่านอย่างเดียว แต่ใน \code{top} กด \code{k} เพื่อส่ง
        signal และกด \code{r} เพื่อ renice ได้ทันทีโดยไม่ต้องออกจากโปรแกรม
        จึงเป็นเครื่องมือที่ครบวงจรกว่าเมื่อต้องแก้ปัญหาเฉพาะหน้า
        เช่นเจอ process ที่กิน CPU ผิดปกติแล้วต้องจัดการเดี๋ยวนั้น
\end{itemize}

\subsubsection{จุดประสงค์}

\code{nice} คือคำสั่งที่ใช้ \textbf{บอกใบ้ (hint) ให้ scheduler ทราบว่า process
ตัวนี้สำคัญมากหรือน้อยเพียงใด} เมื่อเทียบกับ process อื่นที่กำลังแย่ง CPU กันอยู่
โดยกำหนดผ่านตัวเลขที่เรียกว่า \emph{nice value} หรือ \emph{niceness}

\begin{itemize}[leftmargin=*]
  \item ช่วงค่าคือ \textbf{$-20$ ถึง $+19$} ค่าตั้งต้นของทุก process คือ \textbf{0}
  \item ค่า \textbf{ยิ่งมาก ยิ่งใจดี} คือยอมสละ CPU ให้คนอื่นใช้ก่อน
        ตัวเองจึงได้ priority \emph{ต่ำ}
  \item ค่า \textbf{ยิ่งน้อย (ติดลบ) ยิ่งเห็นแก่ตัว} คือแย่ง CPU มาใช้ก่อน
        ตัวเองจึงได้ priority \emph{สูง}
\end{itemize}

จุดที่ต้องเน้นคือ \code{nice} \textbf{ไม่ใช่การจองหรือจำกัดโควตา CPU}
ถ้าไม่มีใครแย่ง CPU อยู่ process ที่ \code{nice} เป็น 19 ก็ยังใช้ CPU ได้เต็ม 100\%
ค่า \code{nice} จะมีผลก็ต่อเมื่อเกิดการแข่งขันแย่ง CPU ขึ้นจริงเท่านั้น
(ข้อสรุปนี้พิสูจน์ด้วยตัวเลขในหัวข้ออภิปรายผล)

การใช้งานที่พบบ่อยคือสั่งงานหนักที่ ``ไม่รีบ'' เช่นการ backup, การ compile
โปรเจกต์ใหญ่ หรือการ encode วิดีโอ ให้ทำงานด้วยค่า \code{nice} สูง ๆ
เพื่อให้งานเหล่านั้นใช้ CPU เฉพาะตอนที่เครื่องว่าง และไม่ไปแย่ง CPU
จนหน้าจอผู้ใช้กระตุก

\subsubsection{วิธี nice process}

มีอยู่สองกรณีตามจังหวะเวลา

\textbf{กรณีที่ 1: กำหนดตั้งแต่ตอนเริ่มโปรแกรม} ใช้คำสั่ง \code{nice}

\begin{lstlisting}[style=terminal,caption={รูปแบบการใช้ \code{nice}}]
$ nice -n <value> <command> [arguments...]

$ nice -n 19 ./q1_burn 15 LOW      # start the program with nice = 19
$ nice ./q1_burn 15 LOW            # without -n the default is nice = 10
\end{lstlisting}

\textbf{กรณีที่ 2: เปลี่ยนค่าของ process ที่รันอยู่แล้ว} ใช้คำสั่ง \code{renice}

\begin{lstlisting}[style=terminal,caption={รูปแบบการใช้ \code{renice}}]
$ renice -n <value> -p <PID>       # one process at a time
$ renice -n <value> -u <username>  # every process owned by that user
$ renice -n <value> -g <PGID>      # every process in that process group
\end{lstlisting}

นอกจากนี้ยังเปลี่ยนได้จากหน้าจอ \code{top} โดยกดปุ่ม \code{r} แล้วพิมพ์ PID
กับค่าใหม่ ซึ่งเบื้องหลังก็คือการเรียก system call \code{setpriority()} เหมือนกัน

\textbf{ข้อจำกัดด้านสิทธิ์} \quad ผู้ใช้ทั่วไป \textbf{เพิ่ม} ค่า \code{nice}
ได้เสมอ (ยอมเสียเปรียบตัวเอง) แต่ \textbf{ลด} ค่าไม่ได้เลย แม้จะเป็นการลด
กลับมาที่ค่าเดิมของ process ตัวเอง การลดค่า \code{nice} ต้องเป็น \code{root}
หรือมีสิทธิ์ \code{CAP\_SYS\_NICE} เท่านั้น เหตุผลคือถ้าใครก็ตั้งค่าติดลบได้
ทุกคนก็จะตั้งเป็น $-20$ กันหมด กลไกนี้ก็จะไร้ความหมาย

\subsubsection{Source code ของโปรแกรมที่ใช้ทดลอง}

เพื่อวัดผลของ \code{nice} เป็นตัวเลข ได้เขียนโปรแกรม \code{q1\_burn.c}
ที่วนคำนวณกิน CPU ตามเวลาที่กำหนด แล้วรายงานว่าทำงานได้กี่ ``รอบ''
ถ้ารัน 2 process พร้อมกัน อัตราส่วนของจำนวนรอบก็คืออัตราส่วนของ CPU
ที่ scheduler แบ่งให้แต่ละตัวโดยตรง

\begin{lstlisting}[caption={q1\_burn.c -- CPU burner สำหรับวัดผลของ nice},label={lst:q1_burn}]
/* CPE 333 PS03 - Q1
 * CPU burner used to demonstrate nice / renice / kill.
 * Usage: ./q1_burn <seconds> <label>
 *
 * It spins for <seconds> of wall clock time and reports how many rounds of
 * work it managed to finish. Two burners started together therefore report
 * numbers that can be compared directly: the ratio of the two round counts
 * is the ratio of the CPU share the scheduler gave them.
 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/resource.h>
#include <sys/time.h>

#define WORK_PER_ROUND 200000

int main(int argc, char *argv[])
{
    int seconds = (argc > 1) ? atoi(argv[1]) : 10;
    const char *label = (argc > 2) ? argv[2] : "burn";

    struct timeval start, now;
    gettimeofday(&start, NULL);

    unsigned long long rounds = 0;
    double sum = 0.0;
    double elapsed;

    for (;;) {
        for (int i = 0; i < WORK_PER_ROUND; i++)   /* one round of pure CPU work */
            sum += i * 0.5;
        rounds++;

        gettimeofday(&now, NULL);
        elapsed = (now.tv_sec - start.tv_sec)
                + (now.tv_usec - start.tv_usec) / 1e6;
        if (elapsed >= seconds)
            break;
    }

    int ni = getpriority(PRIO_PROCESS, 0);   /* the nice value we are running at */

    (void)sum;   /* compiled with -O0, so the work loop is never optimized away */

    printf("[%s] pid=%d nice=%d rounds=%llu wall=%.2fs\n",
           label, getpid(), ni, rounds, elapsed);
    fflush(stdout);
    return 0;
}
\end{lstlisting}

\textbf{คำอธิบายการทำงาน}: โปรแกรมวนลูปคำนวณเลขทศนิยม \code{WORK\_PER\_ROUND}
ครั้งนับเป็นหนึ่งรอบ แล้วเช็คนาฬิกาด้วย \code{gettimeofday()} ว่าครบเวลาที่สั่ง
หรือยัง เมื่อครบจึงอ่านค่า \code{nice} ของตัวเองด้วย \code{getpriority()}
แล้วพิมพ์จำนวนรอบที่ทำได้ออกมา คอมไพล์ด้วย \code{-O0} เพื่อไม่ให้คอมไพเลอร์
ตัดลูปคำนวณทิ้ง

  \item \textbf{ค่า \code{nice} เท่ากัน scheduler แบ่ง CPU ให้เท่ากันจริง}:
        กรณีควบคุมได้ 19{,}068 กับ 19{,}119 รอบ ต่างกันเพียง 0.27\%

        เกิดจากค่า \code{nice} จริง ๆ ไม่ใช่ความบังเอิญของเครื่อง

  \item \textbf{ค่า \code{nice} ต่างกันสร้างความต่างมหาศาล}:
        เมื่อเปลี่ยนเพียงค่า \code{nice} ของตัวหนึ่งเป็น 19

        ตัวเลขนี้ยืนยันว่า \code{nice} มีผลจริงและมีผลมาก
        ค่า \code{\%CPU} ที่ \code{ps} รายงาน (\code{106} เทียบกับ \code{1.7})
        และ \code{TIME+} ที่ \code{top} รายงาน (\code{0:04.48} เทียบกับ
        \code{0:00.07}) ก็ชี้ไปทางเดียวกัน

  \item \textbf{\code{nice} มีความหมายเฉพาะตอนที่มีการแย่ง CPU เท่านั้น}:
        เป็นข้อสรุปที่ตัวเลขในตารางแสดงชัดที่สุด process
        \code{renice\_target} ถูกตั้งเป็น \code{nice} 15 ซึ่งถือว่า
        ``ใจดี'' มาก แต่เพราะรันอยู่ตัวเดียวไม่มีใครแย่ง จึงทำได้ถึง

        ถ้า CPU ยังเหลือ ทุกคนก็ได้ใช้เต็มที่ไม่ว่าค่า \code{nice} จะเป็นเท่าใด

  \item \textbf{CPU หนึ่งแกนถูกใช้จนเต็มในทุกกรณี ต่างกันแค่วิธีแบ่ง}:
        เมื่อรวมผลงานของสอง process ในกรณีควบคุมเข้าด้วยกันจะได้
        $1{,}271 + 1{,}275 = 2{,}546$ รอบต่อวินาที ซึ่งเท่ากับกรณีที่มี
        process เดียวครองแกนนั้นทั้งแกน (2{,}555 รอบต่อวินาที)
        โดยต่างกันเพียง 0.4\% แปลว่า scheduler ไม่ได้ทำให้งานรวมลดลง
        เพียงแต่แบ่งเค้กก้อนเดิมออกเป็นสองส่วนเท่า ๆ กัน
        ส่วนในกรณีทดลองก็เป็นเค้กก้อนเดิม เพียงแต่ถูกแบ่งเป็น
        64 ต่อ 1 ตามค่า \code{nice} ที่ตั้งไว้

  \item \textbf{ความสัมพันธ์ระหว่างคอลัมน์ \code{NI}, \code{PRI} และ \code{PR}}:
        จากผลการทดลองสรุปได้ว่าคอลัมน์ \code{PRI} ของ \code{ps} มีค่าเท่ากับ
        $19 - \code{NI}$ (nice 0 ได้ PRI 19, nice 15 ได้ PRI 4, nice 19 ได้ PRI 0
        และ \code{systemd-journald} ที่ nice $-1$ ได้ PRI 20)
        ส่วนคอลัมน์ \code{PR} ของ \code{top} มีค่าเท่ากับ $20 + \code{NI}$
        (nice 0 ได้ PR 20, nice 19 ได้ PR 39) นั่นคือทั้งสองคำสั่งแสดงข้อมูล
        ชุดเดียวกันแต่ ``กลับด้าน'' กัน ของ \code{ps} ยิ่งมากยิ่งสำคัญ
        ส่วนของ \code{top} เป็นเลข priority ดิบของเคอร์เนลซึ่งยิ่งน้อยยิ่งสำคัญ
        เวลาอ่านรายงานจึงต้องดูให้ดีว่ากำลังอ่านคอลัมน์ของคำสั่งไหน

  \item \textbf{คอลัมน์ \code{STAT} มีตัวอักษร \code{N} เพิ่มเข้ามา}:
        สังเกตว่า process ที่ \code{nice} มากกว่า 0 จะมีสถานะเป็น \code{RN+}

        มีใครถูก renice ไว้บ้าง

  \item \textbf{สิทธิ์เป็นแบบทางเดียว}: การทดลองที่ 5 แสดงว่าผู้ใช้ทั่วไป

        (\code{renice 0} กลับล้มเหลว ทั้งที่เป็น process ของตัวเองแท้ ๆ)
        พฤติกรรมนี้เป็นไปตามที่ระบุใน \code{man 2 setpriority} และเป็นการป้องกัน
        ไม่ให้ผู้ใช้คนใดคนหนึ่งตั้งค่าติดลบเพื่อยึด CPU ทั้งเครื่องไว้เอง
        อีกจุดที่น่าสนใจคือคำสั่ง \code{nice -n -5 nice} แม้จะตั้งค่าไม่สำเร็จ
        แต่ยัง \emph{รันโปรแกรมต่อ} ด้วยค่า nice เดิม (พิมพ์ \code{0} ออกมา)
        ไม่ได้ยกเลิกการทำงานทิ้ง
\end{itemize}

\subsubsection{Source code ของโปรแกรมที่ใช้ทดลอง}

เพื่อพิสูจน์ว่า \code{SIGTERM} ดักจับได้แต่ \code{SIGKILL} ดักจับไม่ได้
ได้เขียนโปรแกรม \code{q1\_sigdemo.c} ที่ ``ดื้อ'' คือดักจับ \code{SIGTERM}
และ \code{SIGINT} ไว้แล้วไม่ยอมตาย

\begin{lstlisting}[caption={q1\_sigdemo.c -- process ที่ดักจับสัญญาณและไม่ยอมจบการทำงาน},label={lst:q1_sigdemo}]
/* CPE 333 PS03 - Q1
 * A process that catches SIGTERM and SIGINT and refuses to exit,
 * used to show why SIGKILL (kill -9) exists.
 */
#include <stdio.h>
#include <signal.h>
#include <unistd.h>

static const char msg_term[] = "[sigdemo] caught SIGTERM (15) -- handler ran, still alive\n";
static const char msg_int[]  = "[sigdemo] caught SIGINT  (2)  -- handler ran, still alive\n";

static void handler(int sig)
{
    /* write() is async-signal-safe, printf() is not */
    if (sig == SIGTERM)
        write(STDOUT_FILENO, msg_term, sizeof msg_term - 1);
    else
        write(STDOUT_FILENO, msg_int, sizeof msg_int - 1);
}

int main(void)
{
    signal(SIGTERM, handler);
    signal(SIGINT, handler);

    printf("[sigdemo] pid = %d, catching SIGTERM(15) and SIGINT(2)\n", getpid());
    fflush(stdout);

    for (;;)
        pause();     /* sleep until a signal arrives */

    return 0;
}
\end{lstlisting}

\textbf{คำอธิบายการทำงาน}: ลงทะเบียนฟังก์ชัน \code{handler()} ไว้กับ
\code{SIGTERM} และ \code{SIGINT} ด้วย \code{signal()} จากนั้นวนเรียก
\code{pause()} ซึ่งจะทำให้ process หลับรอจนกว่าจะมีสัญญาณเข้ามา
เมื่อสัญญาณมาถึง \code{handler()} จะถูกเรียก พิมพ์ข้อความ แล้ว \code{pause()}
ก็จะกลับมาวนรออีกครั้ง process จึงไม่มีวันจบด้วยสองสัญญาณนี้
ในตัว handler ใช้ \code{write()} แทน \code{printf()} เพราะ \code{write()}
เป็น async-signal-safe ส่วน \code{printf()} ไม่ใช่ การเรียก \code{printf()}
ใน handler ขณะที่โปรแกรมหลักกำลังใช้ buffer อยู่อาจทำให้ข้อมูลเสียหายได้

$ kill -0 5837   -> bash: kill: (5837) - No such process (exit status 1)
\end{lstlisting}

\subsubsection{อภิปรายผล}

\begin{itemize}[leftmargin=*]
  \item \textbf{\code{SIGTERM} คือการ ``ขอ'' ส่วน \code{SIGKILL} คือการ ``บังคับ''}:
        การทดลองที่ 2 แสดงให้เห็นชัดว่า \code{kill} ธรรมดาส่ง \code{SIGTERM}
        ซึ่งโปรแกรมมีสิทธิ์ดักจับและตัดสินใจเองว่าจะทำอย่างไร
        \code{q1\_sigdemo} เลือกที่จะพิมพ์ข้อความแล้วอยู่ต่อ ทำให้คำสั่ง
        \code{kill} และ \code{kill -INT} ไม่มีผลใด ๆ ต่อการมีอยู่ของ process
        จนต้องใช้ \code{kill -9} ซึ่งเคอร์เนลเป็นผู้จัดการให้เอง
        โปรแกรมไม่มีโอกาสแม้แต่จะรู้ตัว

  \item \textbf{ควรใช้ \code{kill} ก่อนเสมอ และใช้ \code{kill -9} เป็นทางเลือกสุดท้าย}:
        เหตุผลคือ \code{SIGTERM} เปิดโอกาสให้โปรแกรมทำ cleanup ก่อนจบ เช่น
        เขียนข้อมูลใน buffer ลงไฟล์ ปิด socket ลบไฟล์ชั่วคราว หรือปลด lock
        ส่วน \code{SIGKILL} ตัดจบทันที ทำให้ไฟล์ชั่วคราวค้าง ฐานข้อมูลอาจไม่ถูก
        commit และ process ลูกอาจกลายเป็น orphan ตามที่ได้ศึกษาใน PS02
        ในทางปฏิบัติควรลอง \code{kill PID} แล้วรอสัก 5--10 วินาที
        ถ้ายังไม่ตายจึงค่อยใช้ \code{kill -9 PID}

  \item \textbf{\code{SIGSTOP} ไม่ใช่การฆ่า และไม่ใช่การ ``หยุดถาวร''}:
        การทดลองที่ 3 แสดงว่า process เปลี่ยนสถานะจาก \code{S} เป็น \code{T}
        แล้วกลับมาเป็น \code{S} ได้ด้วย \code{SIGCONT} ในระหว่างที่เป็น \code{T}
        process ยังคงอยู่ในระบบและยังจองหน่วยความจำอยู่เหมือนเดิม
        เพียงแต่ scheduler จะไม่จัด CPU ให้อีกจนกว่าจะได้ \code{SIGCONT}
        ประโยชน์จริงคือใช้ ``แช่แข็ง'' งานหนักไว้ชั่วคราวเมื่อต้องการ CPU
        ไปทำอย่างอื่นก่อน แล้วค่อยปลุกกลับมาโดยไม่ต้องเริ่มงานใหม่ทั้งหมด
        (สัญญาณคู่นี้คือกลไกเบื้องหลังคำสั่ง \code{CTRL+Z}, \code{fg}, \code{bg}
        ซึ่งจะทดลองต่อในข้อ 2)

  \item \textbf{\code{\%n} เป็นของ shell ไม่ใช่ของเคอร์เนล}:
        เคอร์เนลรู้จักแต่ PID เท่านั้น เลข job \code{[1] [2] [3]} เป็นสิ่งที่
        shell จดไว้เองสำหรับ process ที่ตัวเองสร้าง เวลาสั่ง \code{kill \%2}
        shell จะแปลง \code{\%2} เป็น PID (หรือ process group) แล้วค่อยส่งสัญญาณ
        ผลที่ตามมาคือ \textbf{job spec ใช้ได้เฉพาะใน shell ที่เป็นเจ้าของ job นั้น}
        ถ้าเปิด terminal ใหม่แล้วสั่ง \code{kill \%1} จะไม่พบ job
        ต้องกลับไปใช้ PID แทน ข้อดีของ \code{\%n} คือสะดวกและอ้างได้หลายตัว
        พร้อมกันดังที่ทดลองด้วย \code{kill -9 \%1 \%3}

  \item \textbf{\code{pkill -f} สะดวกแต่ต้องระวังมาก}:
        option \code{-f} สั่งให้จับคู่กับ \emph{command line เต็ม} ไม่ใช่แค่ชื่อ
        โปรแกรม ซึ่งกว้างกว่าที่คิดมาก ระหว่างการเก็บผลการทดลองนี้เกิดปัญหาจริง
        คือสคริปต์ที่สั่ง \code{pkill -f 'sleep 700'} ได้ฆ่า \emph{ตัวเอง} ไปด้วย
        เพราะ command line ของสคริปต์นั้นมีข้อความ \code{sleep 700} ประกอบอยู่
        จึงเข้าเงื่อนไขไปด้วย ทำให้ผลการทดลองขาดหายไปครึ่งหนึ่ง
        แนวปฏิบัติที่ปลอดภัยคือ \textbf{สั่ง \code{pgrep} ด้วยเงื่อนไขเดียวกันก่อน}
        เพื่อดูรายชื่อเป้าหมาย แล้วจึงเปลี่ยนเป็น \code{pkill} เมื่อมั่นใจแล้ว
        ซึ่งเป็นลำดับที่ใช้ในการทดลองที่ 5

  \item \textbf{\code{killall} ปลอดภัยกว่าแต่แคบกว่า}:
        \code{killall} จับคู่กับ \emph{ชื่อโปรแกรม} แบบตรงตัว จึงไม่พลาดไปโดน
        คำสั่งอื่นที่บังเอิญมีข้อความคล้ายกันเหมือน \code{pkill -f}
        แต่ก็แลกมาด้วยความยืดหยุ่นที่น้อยกว่า และต้องระวังว่าบนระบบ UNIX
        บางตระกูล (เช่น Solaris) คำสั่งชื่อเดียวกันนี้หมายถึงการฆ่า
        \emph{ทุก process ในระบบ} ซึ่งอันตรายมาก

  \item \textbf{\code{kill -0} เป็นเครื่องมือตรวจสอบ ไม่ใช่การฆ่า}:
        เป็นสำนวนมาตรฐานที่ใช้ในสคริปต์เพื่อถามว่า PID ยังอยู่หรือไม่
        โดยไม่ก่อผลข้างเคียง ค่า exit status 0 แปลว่ายังอยู่และเรามีสิทธิ์ส่ง
        สัญญาณ ส่วน 1 แปลว่าไม่พบ process นั้นแล้ว มักใช้คู่กับการรอให้ process
        จบหลังส่ง \code{SIGTERM} ก่อนตัดสินใจว่าจะต้องใช้ \code{SIGKILL} หรือไม่

  \item \textbf{เรื่องสิทธิ์}: ผู้ใช้ทั่วไปส่งสัญญาณได้เฉพาะ process ของตัวเอง
        การพยายามส่งให้ process ของผู้ใช้อื่นหรือของ \code{root} จะได้
        \code{Operation not permitted} ต้องใช้ \code{sudo} เท่านั้น
        และแม้แต่ \code{root} ก็ฆ่า process ที่ติดอยู่ในสถานะ \code{D}
        (uninterruptible sleep เช่นค้างรอ I/O) ด้วย \code{kill -9} ไม่ได้
        เพราะสัญญาณจะถูกส่งไปรอไว้เฉย ๆ จนกว่า process จะออกจากสถานะนั้น
\end{itemize}

\section{การรัน shell script แบบ foreground / background และการควบคุม job}
% =====================================================================

ข้อนี้ศึกษาสองสถานการณ์ที่ต่อยอดจากข้อ 1 โดยตรง คือ (1) ความต่างระหว่างการรัน
script แบบธรรมดากับการเติมเครื่องหมาย \code{\&} ต่อท้าย และ (2) การหยุด script
กลางคันด้วย \code{CTRL+Z} แล้วปลุกกลับมาด้วย \code{fg} หรือ \code{bg}

\vspace{0.5em}

\textbf{หมายเหตุเรื่องวิธีเก็บผล} \quad การกด \code{CTRL+Z} และคำสั่ง \code{jobs},
\code{fg}, \code{bg} ทำงานได้ก็ต่อเมื่อ shell เปิดโหมด \emph{job control} ไว้
ซึ่งเปิดเฉพาะตอนที่ shell เป็นแบบ interactive และมี terminal จริงเท่านั้น
ถ้าสั่งจากสคริปต์ธรรมดาจะได้ข้อความ \code{no job control in this shell}
การเก็บผลข้อนี้จึงใช้คำสั่ง \code{script(1)} สร้าง pseudo terminal ขึ้นมาจริง ๆ
แล้วเปิด \code{bash --norc -i} บนนั้น จากนั้นป้อนคำสั่งเข้าไปทีละบรรทัด
โดยเว้นจังหวะเหมือนคนพิมพ์ ส่วน \code{CTRL+Z} ส่งเป็นไบต์ \code{0x1A} ตรง ๆ
เข้าไปที่ terminal ซึ่ง line discipline ของ tty จะแปลงเป็นสัญญาณ
\code{SIGTSTP} ให้เอง transcript ที่ยกมาทั้งหมดจึงเป็นของ terminal จริง
ไม่ใช่การจำลอง (ตัวสคริปต์เก็บผลอยู่ที่ \code{PS03/src/run\_q2.sh})

#!/bin/bash
# CPE 333 PS03 - Q2, first situation
# Calls "sleep" for a total of 10 seconds, one second per iteration,
# so the progress can be watched while the script is running.

echo "[ss1_1] start  pid=$$  at $(date +%T)"

for i in $(seq 1 10); do

    echo "[ss1_1] tick $i/10"
done

echo "[ss1_1] done   pid=$$  at $(date +%T)"

\subsubsection{เรื่องสิทธิ์ในการรัน (\code{chmod})}

ไฟล์ที่เพิ่งสร้างใหม่จะได้สิทธิ์ \code{rw-r--r--} (\code{644}) ตามค่า
\code{umask} มาตรฐาน คือไม่มีบิต \code{x} เคอร์เนลจึงปฏิเสธที่จะ \code{exec}
ไฟล์นั้น ต้องเพิ่มบิต \code{x} ด้วย \code{chmod} ก่อน

\begin{lstlisting}[style=terminal,caption={Permission denied และการแก้ด้วย chmod}]

\begin{itemize}[leftmargin=*]
  \item \textbf{ความต่างที่แท้จริงคือ ``ใครเป็นเจ้าของ terminal''}:
        ไม่ใช่แค่เรื่องรอหรือไม่รอ ผลจาก \code{ps} ชี้ชัดว่าตอนรันแบบ foreground
        คอลัมน์ \code{TPGID} ของทุก process มีค่าเป็น \code{6860}
        ซึ่งคือ \code{PGID} ของ \code{ss1\_1.sh} เอง แปลว่า kernel ยกสิทธิ์
        ควบคุม terminal ให้ process group ของสคริปต์ไปแล้ว
        และ \code{STAT} ของสคริปต์กับ \code{sleep} ลูกของมันมีเครื่องหมาย
        \code{+} ต่อท้าย (\code{S+}) ซึ่งเป็นสัญลักษณ์ที่ \code{ps} ใช้บอกว่า
        ``process นี้อยู่ใน foreground process group''
        ในทางกลับกันตอนรันแบบ background \code{TPGID} ไม่ใช่ของสคริปต์
        และ \code{STAT} เป็น \code{S} เฉย ๆ ไม่มี \code{+}

  \item \textbf{shell ไม่ได้ ``หยุดทำงาน'' ตอน foreground แต่ ``รออยู่''}:
        บรรทัด \code{6844 ... 6860 Ss} แสดงว่า shell ยังอยู่ในสถานะ \code{S}
        (sleeping) คือถูกบล็อกอยู่ใน \code{wait()} รอให้ลูกจบ ไม่ได้กิน CPU
        เป็นกลไกเดียวกับที่ศึกษาไปแล้วใน PS02 ข้อ 1

  \item \textbf{background ไม่ได้แยก output ออกไป}:
        เป็นจุดที่คนเข้าใจผิดบ่อย ผลการทดลองแสดงชัดว่าข้อความ
        \code{[ss1\_1] start pid=6880} โผล่ขึ้นมาต่อท้าย prompt
        และ \code{[ss1\_1] tick 1/10} แทรกกลางผลลัพธ์ของคำสั่ง \code{ps}
        เพราะ job ที่รันเบื้องหลังยังเขียน stdout ลง terminal เดิม
        ถ้าไม่อยากให้ปนกันต้อง redirect เอง เช่น
        \code{./ss1\_1.sh > out.log 2>\&1 \&}

  \item \textbf{\code{\&} ทำให้ shell จดงานนั้นเป็น job}:
        ทันทีที่สั่ง shell พิมพ์ \code{[1] 6880} ออกมา คือเลข job กับ PID
        ทำให้อ้างถึงด้วย \code{\%1} ได้ในภายหลัง และเมื่องานจบ shell จะแจ้ง
        \code{[1]+ Done} ที่ prompt ถัดไป ถ้าต้องการรอให้จบจริง ๆ
        ต้องสั่ง \code{wait} ดังที่ทดลอง ส่วน exit status ก็ต้องเก็บผ่าน
        \code{wait \%1} หรือ \code{\$!} เพราะไม่มี \code{\$?} ให้ดูทันทีเหมือน foreground

  \item \textbf{ข้อควรระวังเมื่อปิด terminal}:
        job ที่รันด้วย \code{\&} ยังผูกอยู่กับ terminal เดิม เมื่อปิด terminal
        เคอร์เนลจะส่ง \code{SIGHUP} ไปให้ทั้ง session ทำให้งานตายตามไปด้วย
        ถ้าต้องการให้อยู่รอดต้องใช้ \code{nohup ./ss1\_1.sh \&} หรือสั่ง
        \code{disown} เพิ่ม
\end{itemize}

\subsubsection{อภิปรายผล}

\begin{table}[H]
\centering
\caption{สรุปกลไกเบื้องหลัง CTRL+Z, bg และ fg}

\toprule
\textbf{การกระทำ} & \textbf{สัญญาณที่ส่ง} & \textbf{สถานะที่เปลี่ยน} & \textbf{ใครคุม terminal ต่อ} \\
\midrule
\code{CTRL+Z} & \code{SIGTSTP} (20) & \code{S+} $\rightarrow$ \code{T} ทั้ง process group & shell ทวง terminal คืน prompt กลับมา \\
\addlinespace
\code{bg \%1} & \code{SIGCONT} (18) & \code{T} $\rightarrow$ \code{S} (ไม่มี \code{+}) & shell ยังคุมอยู่เหมือนเดิม prompt ใช้ได้ทันที \\
\addlinespace
\code{fg \%1} & \code{SIGCONT} (18) & \code{T} $\rightarrow$ \code{S+} & ยกให้ job แล้วรอจน job จบหรือถูกหยุดอีก \\
\bottomrule
\end{tabular}

\begin{itemize}[leftmargin=*]
  \item \textbf{\code{CTRL+Z} คือการ ``พัก'' ไม่ใช่การ ``ฆ่า''}:
        ผลจาก \code{ps} ยืนยันว่า process ยังอยู่ครบ เพียงแต่เปลี่ยนสถานะ
        จาก \code{S+} เป็น \code{T} (stopped) ต่างจาก \code{CTRL+C}
        ซึ่งส่ง \code{SIGINT} แล้วทำให้ process จบไปเลย
        กลไกนี้คือคู่เดียวกับ \code{kill -STOP} ที่ทดลองไว้ในข้อ 1
        ต่างกันเพียงว่า \code{SIGTSTP} ที่มาจากคีย์บอร์ดนั้น process
        ดักจับได้ ส่วน \code{SIGSTOP} ดักจับไม่ได้

  \item \textbf{สัญญาณถูกส่งถึงทั้ง process group ไม่ใช่แค่ process เดียว}:
        เป็นจุดที่ผลการทดลองแสดงได้ชัดเจนมาก คือทั้ง
        \code{6914 /bin/bash ./ss1\_2.sh} และลูกของมันคือ
        \code{6916 sleep 1000} เปลี่ยนเป็นสถานะ \code{T} พร้อมกัน
        ทั้งที่กด \code{CTRL+Z} เพียงครั้งเดียว เพราะทั้งคู่มี \code{PGID}
        เดียวกันคือ \code{6914} และ terminal ส่งสัญญาณให้ทั้ง
        foreground process group หากเคอร์เนลส่งให้เฉพาะตัว \code{bash}
        ของสคริปต์ ตัว \code{sleep} ก็จะยังนับเวลาต่อไป ซึ่งไม่ใช่สิ่งที่ผู้ใช้คาดหวัง

  \item \textbf{\code{jobs} เป็นตารางของ shell ไม่ใช่ของเคอร์เนล}:
        เครื่องหมายท้ายเลข job มีความหมายคือ \code{+} หมายถึง current job
        (ตัวที่ \code{fg} หรือ \code{bg} จะเลือกถ้าไม่ระบุ \code{\%n})
        และ \code{-} หมายถึง previous job ส่วน \code{jobs -l}
        จะแสดง PID จริงเพิ่มมาให้ ทำให้เชื่อมโยงกับผลของ \code{ps} ได้

  \item \textbf{ความต่างของ \code{fg} กับ \code{bg} อยู่ที่สิทธิ์ควบคุม terminal
        ไม่ใช่ที่การปลุก}: ทั้งสองคำสั่งส่ง \code{SIGCONT} เหมือนกันทุกประการ
        job จึงกลับมาทำงานต่อได้ทั้งคู่ (เห็นได้จากสถานะที่เปลี่ยนจาก \code{T}
        เป็น \code{S} ทั้งสองกรณี) สิ่งที่ต่างคือ \code{bg} ปล่อยให้ shell
        ถือ terminal ไว้เหมือนเดิม prompt จึงกลับมาให้ใช้ทันที
        ส่วน \code{fg} เรียก \code{tcsetpgrp()} ยกสิทธิ์ควบคุม terminal
        ให้ process group ของ job แล้ว shell ก็เข้าไปรอ
        หลักฐานคือภาพจาก \code{ps} ตอนที่ job อยู่ใน foreground
        มี \code{TPGID} เป็น \code{6914} และ \code{STAT} เป็น \code{S+}
        เทียบกับตอน \code{bg} ที่เป็น \code{S} เฉย ๆ

  \item \textbf{มีงานบางประเภทที่ \code{bg} ใช้ไม่ได้เลย}:
        การทดลองสุดท้ายแสดงกรณีนี้ชัดที่สุด job ที่เรียก \code{read}
        เพื่ออ่านคีย์บอร์ดถูกเคอร์เนลหยุดทันทีด้วย \code{SIGTTIN}
        และ \code{jobs} รายงานเหตุผลไว้ตรง ๆ ว่า
        \code{Stopped (tty input)} ที่สำคัญคือเมื่อสั่ง \code{bg \%1}
        job กลับไปหยุดที่เดิมอีกครั้งด้วยเหตุผลเดียวกัน เพราะ \code{bg}
        ให้แค่ \code{SIGCONT} ไม่ได้ให้สิทธิ์อ่าน terminal
        ต้องสั่ง \code{fg \%1} เท่านั้น job จึงอ่านข้อความ \code{CPE333}
        ที่พิมพ์เข้าไปได้และทำงานจนจบ
        สรุปเป็นหลักการได้ว่า \code{bg} เหมาะกับงานที่คำนวณอย่างเดียว
        ส่วนงานที่ต้องโต้ตอบกับผู้ใช้ต้องอยู่ใน foreground เสมอ

  \item \textbf{การ \code{kill} job ที่ถูกหยุดอยู่}:
        \code{SIGTERM} เพียงอย่างเดียวจะไปค้างรออยู่เฉย ๆ เพราะ process
        ที่อยู่ในสถานะ \code{T} ไม่ได้ถูกจัดให้ทำงานจึงยังไม่ได้ประมวลผลสัญญาณ
        แต่ผลการทดลองแสดงว่า job ตายทันที เพราะ \code{kill} ของ bash
        ฉลาดพอที่จะส่ง \code{SIGCONT} ตามไปให้ด้วยเมื่อรู้ว่าเป้าหมายถูกหยุดอยู่
        สังเกตได้จาก \code{jobs -l} ครั้งแรกหลัง \code{kill \%1}
        ที่รายงาน \code{Terminated} และครั้งที่สองไม่เหลืออะไรเลย
        เพราะ shell แจ้งสถานะสุดท้ายของ job เพียงครั้งเดียวแล้วลบทิ้ง

  \item \textbf{เชื่อมโยงกลับไปข้อ 1}: คำสั่ง \code{fg} และ \code{bg}
        แท้จริงแล้วคือหน้ากากที่สวยงามของ \code{kill -CONT} ที่ทดลองไว้ในข้อ 1
        โดย \code{bg \%1} ให้ผลเหมือน \code{kill -CONT <PID>} ทุกประการ
        ส่วน \code{fg \%1} คือ \code{kill -CONT} บวกกับการยก terminal ให้
        ความรู้เรื่องสัญญาณจากข้อ 1 จึงอธิบายพฤติกรรมของ job control
        ในข้อนี้ได้ทั้งหมด
\end{itemize}

\subsection{สรุปข้อ 2}

\begin{enumerate}[leftmargin=*]
  \item การรันแบบ foreground กับ background ต่างกันที่ \emph{ใครถือสิทธิ์ควบคุม
        terminal} ซึ่งตรวจสอบได้ตรง ๆ จากเครื่องหมาย \code{+} ในคอลัมน์
        \code{STAT} และค่าในคอลัมน์ \code{TPGID} ของ \code{ps}
        ส่วนเรื่อง prompt กลับเร็วหรือช้าเป็นเพียงผลพลอยได้

  \item เครื่องหมาย \code{\&} ไม่ได้แยก output ของงานออกไปไหน
        stdout ยังลง terminal เดิมและปนกับ prompt ถ้าต้องการความสะอาด
        ต้อง redirect เอง

  \item \code{CTRL+Z} คือ \code{SIGTSTP} ที่ส่งถึงทั้ง foreground process group
        ทำให้ทั้งสคริปต์และลูกของมันหยุดพร้อมกัน โดย process ยังไม่ตาย

  \item \code{fg} และ \code{bg} ส่งสัญญาณเดียวกันคือ \code{SIGCONT}
        ต่างกันที่ \code{fg} ยกสิทธิ์ควบคุม terminal ให้ job ด้วย
        จึงเป็นทางเลือกเดียวสำหรับงานที่ต้องรับ input จากผู้ใช้
        ส่วน \code{bg} เหมาะกับงานที่ทำงานเงียบ ๆ ได้เอง
\end{enumerate}
