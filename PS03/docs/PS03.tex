\subsubsection{อภิปรายผล}

\begin{itemize}[leftmargin=*]
  \item \textbf{ต่างกันที่มิติเวลาเป็นหลัก}: \code{ps} ตอบว่า ``ณ วินาทีนี้มีอะไรอยู่ในระบบ''
        ส่วน \code{top} ตอบว่า ``ตอนนี้ระบบกำลังทำอะไรอยู่'' ยืนยันได้จากการที่
        \code{ps aux} ใช้เวลา \code{0.00} วินาทีแล้วจบ ในขณะที่ \code{top}
        ต้องถูกบังคับด้วย \code{-n 1} ถึงจะยอมจบ

  \item \textbf{ค่า \code{\%CPU} ของสองคำสั่งไม่ใช่ค่าเดียวกัน}: เป็นจุดที่สับสนบ่อยที่สุด
        ของ \code{ps} คือเวลา CPU ที่ใช้ทั้งหมดหารด้วยอายุ process จึงเป็นค่าเฉลี่ย
        ย้อนหลัง ส่วนของ \code{top} คิดจากส่วนต่างระหว่างสองรอบรีเฟรชล่าสุด
        ผลคือ process ที่เคยกิน CPU หนักเมื่อชั่วโมงก่อนแต่ตอนนี้หลับอยู่
        จะยังมี \code{\%CPU} สูงใน \code{ps} แต่เป็น \code{0.0} ใน \code{top}
        ในการทดลองนี้ \code{ps} รายงาน \code{109} ให้ \code{q1\_burn} ที่เพิ่งเกิดได้
        2 วินาที (คอลัมน์ \code{ELAPSED} ปัดเป็นวินาทีเต็ม จึงหารแล้วเกิน 100 เล็กน้อย)
        ขณะที่ \code{top} รายงาน \code{100.0} ตรงตามจริง

  \item \textbf{\code{top} ให้ภาพรวมของระบบ ส่วน \code{ps} ให้ภาพของ process}:
        load average, จำนวน zombie, \code{\%Cpu(s)} แยก us/sy/ni/id/wa และหน่วยความจำรวม
        มีเฉพาะใน \code{top} ถ้าจะเอาจาก \code{ps} ต้องไปอ่าน \code{/proc/loadavg}
        และ \code{/proc/meminfo} เอง นอกจากนี้ผลการทดลองยังยืนยันว่า \code{top}
        คำนวณใหม่ทุกรอบจริง คือ \code{TIME+} ของ \code{q1\_burn} เพิ่มจาก
        \code{0:02.66} เป็น \code{0:03.76} คือ \code{1.10} วินาทีในเวลาจริง 1 วินาที
        ตรงกับที่รายงาน \code{\%CPU} เป็น \code{100.0} พอดี

  \item \textbf{แต่ละคำสั่งทำสิ่งที่อีกคำสั่งทำไม่ได้}: \code{ps} ชนะขาดเรื่องการนำผล
        ไปใช้ต่อ เพราะต่อ pipe ได้ทันทีและเลือกคอลัมน์เองได้ (ใช้ตลอดทั้งรายงานนี้)
        ส่วน \code{top} ``สั่งการ'' ได้ในตัว กด \code{k} ส่ง signal หรือ \code{r}
        เพื่อ renice ได้โดยไม่ต้องออกจากโปรแกรม จึงครบวงจรกว่าเมื่อต้องแก้ปัญหาเฉพาะหน้า
\end{itemize}

% ---------------------------------------------------------------------
\subsection{จุดประสงค์ของคำสั่ง \code{nice} และวิธี nice process}
% ---------------------------------------------------------------------

\code{nice} ใช้ \textbf{บอกใบ้ให้ scheduler ทราบว่า process ตัวนี้สำคัญมากหรือน้อย}
เมื่อเทียบกับ process อื่นที่แย่ง CPU กันอยู่ ผ่านตัวเลข \emph{nice value}
ช่วง $-20$ ถึง $+19$ ค่าตั้งต้นคือ \code{0} ค่ายิ่งมากยิ่ง ``ใจดี'' คือยอมสละ CPU
ให้คนอื่นก่อน ตัวเองจึงได้ priority ต่ำ ส่วนค่าติดลบคือแย่ง CPU มาใช้ก่อน
จุดที่ต้องเน้นคือ \code{nice} \textbf{ไม่ใช่การจองหรือจำกัดโควตา CPU}
ถ้าไม่มีใครแย่ง process ที่ \code{nice} เป็น 19 ก็ยังใช้ CPU ได้เต็ม 100\%
การใช้งานจริงคือสั่งงานหนักที่ไม่รีบ เช่น backup หรือ compile โปรเจกต์ใหญ่
ให้ทำงานด้วยค่า \code{nice} สูง ๆ เพื่อไม่ให้ไปแย่ง CPU จนหน้าจอผู้ใช้กระตุก

\textbf{วิธี nice process} มีสองกรณีตามจังหวะเวลา คือ (1) กำหนดตั้งแต่เริ่มโปรแกรม
ด้วย \code{nice -n <value> <command>} และ (2) เปลี่ยนของ process ที่รันอยู่แล้วด้วย
\code{renice -n <value> -p <PID>} ซึ่งยังระบุเป็นรายผู้ใช้ (\code{-u}) หรือรายกลุ่ม
(\code{-g}) ได้ด้วย นอกจากนี้ยังเปลี่ยนได้จากหน้าจอ \code{top} โดยกด \code{r}
ซึ่งเบื้องหลังก็คือ system call \code{setpriority()} เหมือนกัน
ส่วน \textbf{ข้อจำกัดด้านสิทธิ์} คือผู้ใช้ทั่วไป \emph{เพิ่ม} ค่า \code{nice}
ได้เสมอ แต่ \emph{ลด} ไม่ได้เลย แม้จะเป็นการลดกลับมาที่ค่าเดิมของ process ตัวเอง
การลดค่าต้องเป็น \code{root} หรือมีสิทธิ์ \code{CAP\_SYS\_NICE}

\begin{itemize}[leftmargin=*]
  \item \textbf{nice เท่ากัน scheduler แบ่ง CPU ให้เท่ากันจริง และ nice ต่างกันสร้างความต่างมหาศาล}:

  \item \textbf{nice มีความหมายเฉพาะตอนที่มีการแย่ง CPU}: เป็นข้อสรุปที่ตัวเลขในตาราง
        แสดงชัดที่สุด \code{renice\_target} ถูกตั้งเป็น \code{nice} 15 ซึ่งถือว่าใจดีมาก
        แต่เพราะรันอยู่ตัวเดียว จึงทำได้ถึง 2{,}555 รอบต่อวินาที ซึ่ง
        \emph{สูงที่สุดในทุกการทดลอง} สูงกว่า \code{HIGH\_nice0} ที่ \code{nice}
        เป็น 0 เสียอีก และเมื่อรวมผลงานของสอง process ในกรณีควบคุมเข้าด้วยกันจะได้
        $1{,}271 + 1{,}275 = 2{,}546$ รอบต่อวินาที ซึ่งเท่ากับกรณีที่มี process
        เดียวครองแกนนั้นทั้งแกน (ต่างกัน 0.4\%) แปลว่า CPU หนึ่งแกนถูกใช้จนเต็ม
        ในทุกกรณี เพียงแต่ถูกแบ่งกันคนละแบบ \code{nice} จึงกำหนดเพียง
        \emph{ลำดับ} ในการแย่ง ไม่ใช่โควตา

  \item \textbf{ความสัมพันธ์ของคอลัมน์ \code{NI}, \code{PRI} และ \code{PR}}:
        จากผลการทดลอง \code{PRI} ของ \code{ps} เท่ากับ $19 - \code{NI}$
        (nice 0 ได้ 19, nice 15 ได้ 4, nice 19 ได้ 0) ส่วน \code{PR} ของ \code{top}
        เท่ากับ $20 + \code{NI}$ (nice 0 ได้ 20, nice 19 ได้ 39) คือแสดงข้อมูล
        ชุดเดียวกันแต่ ``กลับด้าน'' กัน ของ \code{ps} ยิ่งมากยิ่งสำคัญ ส่วนของ
        \code{top} เป็นเลข priority ดิบของเคอร์เนลซึ่งยิ่งน้อยยิ่งสำคัญ
        นอกจากนี้ \code{STAT} ของ process ที่ \code{nice} มากกว่า 0 จะมีตัว \code{N}
        เพิ่มมา (\code{RN+}, \code{SN+}) ใช้ตรวจอย่างรวดเร็วได้ว่ามีใครถูก renice ไว้บ้าง

  \item \textbf{สิทธิ์เป็นแบบทางเดียว}: ผู้ใช้ทั่วไป ``สละสิทธิ์'' ได้เสมอ
        (\code{renice +8} สำเร็จ) แต่ ``ทวงคืน'' ไม่ได้เลย (\code{renice 0} ล้มเหลว
        ทั้งที่เป็น process ของตัวเองแท้ ๆ) เป็นการป้องกันไม่ให้ผู้ใช้คนใดตั้งค่าติดลบ
        เพื่อยึด CPU ทั้งเครื่อง อีกจุดที่น่าสนใจคือ \code{nice -n -5} แม้ตั้งค่าไม่สำเร็จ
        แต่ยัง \emph{รันโปรแกรมต่อ} ด้วยค่าเดิม ไม่ได้ยกเลิกการทำงานทิ้ง
\end{itemize}

\subsubsection{อภิปรายผล}

\begin{itemize}[leftmargin=*]
  \item \textbf{\code{SIGTERM} คือการ ``ขอ'' ส่วน \code{SIGKILL} คือการ ``บังคับ''}:
        \code{q1\_sigdemo} เลือกที่จะพิมพ์ข้อความแล้วอยู่ต่อ ทำให้ \code{kill}
        และ \code{kill -INT} ไม่มีผลใด ๆ ต่อการมีอยู่ของ process จนต้องใช้
        \code{kill -9} ซึ่งเคอร์เนลจัดการให้เอง โปรแกรมไม่มีโอกาสแม้แต่จะรู้ตัว
        ในทางปฏิบัติจึงควรใช้ \code{kill} ก่อนเสมอ เพราะ \code{SIGTERM}
        เปิดโอกาสให้โปรแกรมเก็บกวาดก่อนจบ เช่นเขียน buffer ลงไฟล์ ปิด socket
        หรือปลด lock ส่วน \code{kill -9} ตัดจบทันทีทำให้ไฟล์ชั่วคราวค้างและ
        process ลูกอาจกลายเป็น orphan จึงควรใช้เป็นทางเลือกสุดท้ายหลังรอสัก 5--10 วินาที

  \item \textbf{\code{SIGSTOP} ไม่ใช่การฆ่าและไม่ใช่การหยุดถาวร}: process เปลี่ยนสถานะ
        จาก \code{S} เป็น \code{T} แล้วกลับมาเป็น \code{S} ได้ด้วย \code{SIGCONT}
        ระหว่างที่เป็น \code{T} process ยังอยู่ในระบบและยังจองหน่วยความจำเหมือนเดิม
        เพียงแต่ scheduler จะไม่จัด CPU ให้ ประโยชน์จริงคือใช้แช่แข็งงานหนักไว้ชั่วคราว
        แล้วค่อยปลุกกลับมาโดยไม่ต้องเริ่มงานใหม่ (สัญญาณคู่นี้คือกลไกเบื้องหลัง
        \code{CTRL+Z}, \code{fg} และ \code{bg} ที่ทดลองต่อในข้อ 2)

  \item \textbf{\code{\%n} เป็นของ shell ไม่ใช่ของเคอร์เนล}: เคอร์เนลรู้จักแต่ PID
        เลข job \code{[1] [2] [3]} เป็นสิ่งที่ shell จดไว้เองสำหรับ process ที่ตัวเองสร้าง
        เวลาสั่ง \code{kill \%2} shell จะแปลงเป็น PID แล้วค่อยส่งสัญญาณ ผลที่ตามมาคือ
        job spec ใช้ได้เฉพาะใน shell ที่เป็นเจ้าของ job นั้น ถ้าเปิด terminal ใหม่
        ต้องกลับไปใช้ PID แทน ข้อดีคือสะดวกและอ้างได้หลายตัวพร้อมกันดังที่ทดลองด้วย
        \code{kill -9 \%1 \%3}

  \item \textbf{\code{pkill -f} สะดวกแต่ต้องระวังมาก}: option \code{-f} จับคู่กับ
        \emph{command line เต็ม} ซึ่งกว้างกว่าที่คิด ระหว่างเก็บผลการทดลองนี้เกิดปัญหาจริง
        คือสคริปต์ที่สั่ง \code{pkill -f 'sleep 700'} ได้ฆ่า \emph{ตัวเอง} ไปด้วย
        เพราะ command line ของสคริปต์มีข้อความนั้นประกอบอยู่ ทำให้ผลการทดลองขาดไปครึ่งหนึ่ง
        แนวปฏิบัติที่ปลอดภัยคือสั่ง \code{pgrep} ด้วยเงื่อนไขเดียวกันดูก่อนเสมอ
        แล้วจึงเปลี่ยนเป็น \code{pkill} ส่วน \code{killall} จับคู่กับชื่อโปรแกรมแบบตรงตัว
        จึงปลอดภัยกว่าแต่ยืดหยุ่นน้อยกว่า และต้องระวังว่าบน UNIX บางตระกูล
        (เช่น Solaris) คำสั่งชื่อเดียวกันนี้หมายถึงการฆ่าทุก process ในระบบ

  \item \textbf{เรื่องสิทธิ์และข้อยกเว้น}: ผู้ใช้ทั่วไปส่งสัญญาณได้เฉพาะ process ของตัวเอง
        และแม้แต่ \code{root} ก็ฆ่า process ที่ติดอยู่ในสถานะ \code{D}
        (uninterruptible sleep เช่นค้างรอ I/O) ด้วย \code{kill -9} ไม่ได้
        เพราะสัญญาณจะถูกพักไว้จนกว่า process จะออกจากสถานะนั้น
        ส่วน \code{kill -0} เป็นสำนวนมาตรฐานในสคริปต์ที่ใช้ถามว่า PID ยังอยู่ไหม
        โดยไม่ก่อผลข้างเคียง มักใช้คู่กับการรอหลังส่ง \code{SIGTERM}
        ก่อนตัดสินใจว่าต้องใช้ \code{SIGKILL} หรือไม่
\end{itemize}

\begin{itemize}[leftmargin=*]
  \item \textbf{ความต่างที่แท้จริงคือ ``ใครเป็นเจ้าของ terminal'' ไม่ใช่แค่รอหรือไม่รอ}:
        ผลจาก \code{ps} ชี้ชัดว่าตอนรันแบบ foreground คอลัมน์ \code{TPGID}
        ของทุก process มีค่าเป็น \code{6860} ซึ่งคือ \code{PGID} ของ
        \code{ss1\_1.sh} เอง แปลว่าเคอร์เนลยกสิทธิ์ควบคุม terminal ให้ process group
        ของสคริปต์ไปแล้ว และ \code{STAT} ของสคริปต์กับ \code{sleep} ลูกของมัน
        มีเครื่องหมาย \code{+} ต่อท้าย (\code{S+}) ซึ่ง \code{ps} ใช้บอกว่า
        ``อยู่ใน foreground process group'' ในทางกลับกันตอนรันแบบ background
        \code{TPGID} ไม่ใช่ของสคริปต์และ \code{STAT} เป็น \code{S} เฉย ๆ
        นอกจากนี้บรรทัด \code{6844 ... 6860 Ss} ยังแสดงว่า shell ไม่ได้หยุดทำงาน
        แต่ถูกบล็อกอยู่ใน \code{wait()} รอให้ลูกจบ ซึ่งไม่กิน CPU

  \item \textbf{background ไม่ได้แยก output ออกไป}: เป็นจุดที่เข้าใจผิดบ่อย
        ผลการทดลองแสดงชัดว่าข้อความ \code{[ss1\_1] start pid=6880} โผล่ต่อท้าย prompt
        และ \code{[ss1\_1] tick 1/10} แทรกกลางผลลัพธ์ของ \code{ps}
        เพราะ job เบื้องหลังยังเขียน stdout ลง terminal เดิม ถ้าไม่อยากให้ปนกัน
        ต้อง redirect เอง เช่น \code{./ss1\_1.sh > out.log 2>\&1 \&}

  \item \textbf{\code{\&} ทำให้ shell จดงานนั้นเป็น job}: shell พิมพ์ \code{[1] 6880}
        คือเลข job กับ PID ทำให้อ้างด้วย \code{\%1} ได้ภายหลัง และเมื่องานจบจะแจ้ง
        \code{[1]+ Done} ที่ prompt ถัดไป ส่วน exit status ต้องเก็บผ่าน
        \code{wait \%1} หรือ \code{\$!} เพราะไม่มี \code{\$?} ให้ดูทันทีเหมือน foreground
        ข้อควรระวังคือ job ที่รันด้วย \code{\&} ยังผูกกับ terminal เดิม
        เมื่อปิด terminal เคอร์เนลจะส่ง \code{SIGHUP} ทำให้งานตายตามไปด้วย
        ถ้าต้องการให้อยู่รอดต้องใช้ \code{nohup} หรือ \code{disown}
\end{itemize}

  \item \textbf{\code{CTRL+Z} คือการ ``พัก'' ไม่ใช่การ ``ฆ่า'' และส่งถึงทั้ง process group}:
        \code{ps} ยืนยันว่า process ยังอยู่ครบ เพียงเปลี่ยนสถานะจาก \code{S+}
        เป็น \code{T} ต่างจาก \code{CTRL+C} ที่ส่ง \code{SIGINT} แล้วจบไปเลย
        ที่สำคัญคือทั้ง \code{6914 /bin/bash ./ss1\_2.sh} และลูกของมันคือ
        \code{6916 sleep 1000} เปลี่ยนเป็น \code{T} พร้อมกันทั้งที่กดเพียงครั้งเดียว
        เพราะทั้งคู่มี \code{PGID} เดียวกันคือ \code{6914} และ terminal ส่งสัญญาณ
        ให้ทั้ง foreground process group หากเคอร์เนลส่งให้เฉพาะตัว \code{bash}
        ของสคริปต์ ตัว \code{sleep} ก็จะนับเวลาต่อไป ซึ่งไม่ใช่สิ่งที่ผู้ใช้คาดหวัง

  \item \textbf{ความต่างของ \code{fg} กับ \code{bg} อยู่ที่สิทธิ์ควบคุม terminal
        ไม่ใช่ที่การปลุก}: ทั้งสองคำสั่งส่ง \code{SIGCONT} เหมือนกันทุกประการ
        job จึงกลับมาทำงานต่อได้ทั้งคู่ (สถานะเปลี่ยนจาก \code{T} เป็น \code{S}
        ทั้งสองกรณี) สิ่งที่ต่างคือ \code{bg} ปล่อยให้ shell ถือ terminal ไว้เหมือนเดิม
        prompt จึงกลับมาใช้ทันที ส่วน \code{fg} เรียก \code{tcsetpgrp()}

        เป็น \code{6914} และ \code{STAT} เป็น \code{S+} เทียบกับตอน \code{bg}

  \item \textbf{มีงานบางประเภทที่ \code{bg} ใช้ไม่ได้เลย}: การทดลองสุดท้ายแสดงชัดที่สุด

  \item \textbf{การ \code{kill} job ที่ถูกหยุดอยู่ และการเชื่อมโยงกลับไปข้อ 1}:
        \code{SIGTERM} เพียงอย่างเดียวจะค้างรออยู่เฉย ๆ เพราะ process ในสถานะ
        \code{T} ไม่ได้ถูกจัดให้ทำงานจึงยังไม่ประมวลผลสัญญาณ แต่ผลการทดลองแสดงว่า
        job ตายทันที เพราะ \code{kill} ของ bash ส่ง \code{SIGCONT} ตามไปให้ด้วย
        เมื่อรู้ว่าเป้าหมายถูกหยุดอยู่ สังเกตได้จาก \code{jobs -l} ครั้งแรกที่รายงาน
        \code{Terminated} และครั้งที่สองไม่เหลืออะไร เพราะ shell แจ้งสถานะสุดท้าย
        เพียงครั้งเดียวแล้วลบทิ้ง โดยรวมแล้ว \code{fg} และ \code{bg}

        โดย \code{bg \%1} ให้ผลเหมือน \code{kill -CONT <PID>} ทุกประการ
        ส่วน \code{fg \%1} คือ \code{kill -CONT} บวกกับการยก terminal ให้
\end{itemize}

\code{STCF} (Shortest Time-to-Completion First) หรือ \code{SRTF} เป็นนโยบาย
จัดตารางแบบ \emph{preemptive} ที่ทุกหน่วยเวลาจะมอบ CPU ให้ process ซึ่ง
\textbf{เหลืองานน้อยที่สุด} ต่างจาก \code{SJF} ที่เมื่อเริ่มแล้วต้องปล่อยให้ทำจนจบ
งานของข้อนี้คือเขียนฟังก์ชัน \code{simulate\_stfc()} เติมลงในไฟล์ \code{PS3.c}
ที่โจทย์เตรียมไว้ ส่วน \code{main()} ใช้ของเดิมเกือบทั้งหมด แก้เพียงจุดเดียว
ตามที่อธิบายท้ายหัวข้อย่อย Source code (หัวข้อ 3.1)

ยังไม่ได้ใช้ CPU เลย เวลาที่เหลือจึงเท่ากับ \code{burst} เต็ม ๆ กรณี
``มาถึงพร้อมกัน'' จึงเป็นกรณีเฉพาะของ ``เวลาที่เหลือเท่ากัน'' โค้ดจึงเทียบ
\code{pid} เพียงจุดเดียว ส่วน \textbf{รูปแบบผลลัพธ์} นั้นตัวอย่างในโจทย์
ถูกจัดรูปมาไม่สมบูรณ์ (บางบรรทัดขึ้นบรรทัดใหม่คั่นระหว่าง \code{[0-3]:}
กับชื่อ process) แต่สองบรรทัดสุดท้ายที่สมบูรณ์คือ \code{[8-11]: P3}
แสดงว่ารูปแบบที่ถูกต้องคือหนึ่งบรรทัดต่อหนึ่งช่วงเวลา โปรแกรมนี้จึงพิมพ์ตามนั้น
โดยรวมหน่วยเวลาที่ติดกันและเป็นของ process เดียวกันเข้าเป็นช่วงเดียว
และช่วงที่ไม่มี process ใดพร้อมทำงานแสดงเป็น \code{IDLE} ตามตัวอย่างในโจทย์

\subsection{Source code}

\begin{lstlisting}[caption={PS3.c -- ส่วนที่เขียนเพิ่มเข้าไป},label={lst:ps3}]
/* Print one merged time slot. "idx" is the index of the process that owned
 * the CPU during [start, end), or -1 when the CPU was idle. */
static void print_slot(int start, int end, int idx, const Process *procs)
{
    if (start >= end)
        return;                       /* empty slot, before the first decision */

    if (idx < 0)
        printf("[%d-%d]: IDLE\n", start, end);
    else
        printf("[%d-%d]: P%d\n", start, end, procs[idx].pid);
}

void simulate_stfc(Process *procs, int n)
{
    int time = 0;
    int done = 0;

    int current = -1;    /* index of the process on the CPU, -1 = idle */
    int slot_start = 0;  /* time at which the current slot began */

    /* A process with no work to do would never reach remaining == 0 by running,
     * so retire it up front instead of letting it stall the simulation. */
    for (int i = 0; i < n; i++) {
        if (procs[i].remaining <= 0 && !procs[i].finished) {
            procs[i].finished = 1;
            done++;
        }
    }

    while (done < n) {
        /* choose the ready process with the shortest remaining time */
        int pick = -1;
        for (int i = 0; i < n; i++) {
            if (procs[i].finished || procs[i].arrival > time)
                continue;

            if (pick == -1 ||
                procs[i].remaining < procs[pick].remaining ||
                (procs[i].remaining == procs[pick].remaining &&
                 procs[i].pid < procs[pick].pid))
                pick = i;
        }

        /* the owner of the CPU changed, so the previous slot ends here */
        if (pick != current) {
            print_slot(slot_start, time, current, procs);
            slot_start = time;
            current = pick;
        }

        if (pick == -1) {
            time++;      /* nothing has arrived yet, the CPU stays idle */
            continue;
        }

        procs[pick].remaining--;
        time++;

        if (procs[pick].remaining == 0) {
            procs[pick].finished = 1;
            done++;
        }
    }

    print_slot(slot_start, time, current, procs);   /* the last slot */
}
\end{lstlisting}

\textbf{คำอธิบายการทำงาน} \quad ลูปนอกเดินทีละหนึ่งหน่วยเวลาจนกว่าจะครบทุก process
ซึ่งตรงกับนิยามของ STCF ที่ตัดสินใจใหม่ทุกครั้งที่สถานการณ์เปลี่ยน
โดยไม่ต้องแยกกรณีว่าเหตุการณ์ไหนบ้างที่ทำให้ต้องตัดสินใจใหม่
ลูปในเลือกผู้ชนะโดยข้าม process ที่จบแล้วหรือยังมาไม่ถึง แล้วเทียบ \code{remaining}
หากเท่ากันจึงเทียบ \code{pid} ถ้าไม่มีใครพร้อมเลยจะได้ \code{-1} ซึ่งหมายถึง IDLE
การรวมช่วงเวลาใช้ตัวแปร \code{current} กับ \code{slot\_start} เมื่อใดที่ผู้ชนะ
เปลี่ยนไป แสดงว่าช่วงเดิมจบลงที่เวลาปัจจุบันพอดี จึงพิมพ์ช่วงเดิมแล้วเริ่มนับใหม่
ส่วนการพิมพ์ช่วงสุดท้ายต้องทำนอกลูป เพราะตอนที่ process ตัวสุดท้ายจบ
ลูปจะจบทันทีโดยไม่มีการเปลี่ยนผู้ชนะให้ตรวจจับได้อีก

\textbf{จุดเดียวที่แก้ใน \code{main()}} \quad โค้ดเดิมข้ามบรรทัดหัวตารางด้วย
\code{fgets(line, sizeof(line), fp);} โดยไม่ดูค่าที่คืนมา ซึ่งถ้าไฟล์ว่างเปล่า
ตัวแปร \code{line} จะไม่ถูกกำหนดค่า และเมื่อคอมไพล์ด้วย \code{-O2} จะได้ warning
เพราะ \code{fgets()} เป็น \code{warn\_unused\_result} โจทย์เปิดช่องให้แก้ส่วนนี้ได้
(\code{// you may change this if needed}) จึงเพิ่ม
\code{if (!fgets(...)) \{ fprintf(stderr, ...); fclose(fp); return 1; \}}
เข้าไป ผลคือคอมไพล์ผ่านโดยไม่มี warning ทั้งที่ \code{-O0} และ \code{-O2}
และไฟล์ว่างจะได้ข้อความแจ้งที่อ่านรู้เรื่อง

        เทียบกับ 8.00 ของ FIFO และ case2 ได้ 3.50 เทียบกับ 4.25 ส่วน case3

        \emph{ไม่แย่กว่า} ไม่ใช่ว่าต้องดีกว่าเสมอ ในกรณีที่งานสั้นบังเอิญมาถึง
        ตอนที่ CPU ว่างอยู่แล้ว ลำดับที่ได้จากทั้งสองนโยบายก็จะเหมือนกัน
        อย่างไรก็ตามแม้ในเคสนั้น STCF ก็ยังชนะเรื่อง response time (0.33 เทียบกับ 1.00)

  \item \textbf{ราคาที่ต้องจ่ายคือ starvation และการต้องรู้ \code{burst} ล่วงหน้า}:
        case1 แสดงชัดว่า P1 มาถึงก่อนใครเพื่อน (เวลา 0) แต่กลับเป็นตัวสุดท้ายที่จบ
        (เวลา 12) และมีเวลารอสูงสุดคือ 5 หน่วยเวลา เพราะถูกงานที่สั้นกว่าแย่ง CPU
        ไปสองครั้ง ถ้ามีงานสั้นไหลเข้ามาไม่หยุด process ที่มี burst ยาวก็อาจไม่ได้จบเลย
        นอกจากนี้การจำลองนี้ทำได้เพราะไฟล์ \code{.csv} บอก \code{burst} มาให้แล้ว
        แต่ระบบปฏิบัติการจริงไม่มีทางรู้ล่วงหน้า จึงต้องประมาณจากพฤติกรรมในอดีต
        หรือเปลี่ยนไปใช้นโยบายที่ไม่ต้องรู้ \code{burst} เช่น MLFQ
        ที่ค่อย ๆ ลดระดับความสำคัญของงานที่ใช้ CPU นาน ซึ่งให้ผลใกล้เคียง STCF
        โดยไม่ต้องพึ่งข้อมูลอนาคต

  \item \textbf{การแย่ง CPU เกิดเฉพาะตอนที่มี process ใหม่มาถึง}: พิสูจน์ได้ง่าย ๆ
        คือ process ที่กำลังทำงานอยู่มี \code{remaining} ลดลงเรื่อย ๆ
        ส่วนตัวที่รออยู่มีค่าคงที่ ตัวที่กำลังทำงานจึงยังเป็นตัวที่เหลือน้อยที่สุดต่อไปเสมอ
        เว้นแต่มีตัวใหม่ที่เหลือน้อยกว่าโผล่เข้ามา ผลในเชิงการเขียนโปรแกรมคือ
        การเลือกผู้ชนะใหม่ทุกหน่วยเวลาแม้จะดูเปลืองแต่ให้คำตอบที่ถูกต้องเสมอ
        และเขียนง่ายกว่าการไล่จับเหตุการณ์เป็นกรณี ๆ มาก
        อย่างไรก็ตาม \textbf{กฎ tie-break ก็ทำให้เกิดการแย่ง CPU ได้ด้วย}
        เห็นได้จาก case3 ที่เวลา 3 ตอนนั้น P2 กำลังทำงานอยู่และเหลืออีก 2 หน่วย
        พอดีกับที่ P1 มาถึงพร้อม \code{burst} 2 หน่วยเท่ากัน ตามกฎของโจทย์
        P1 จึงได้ CPU ไปทั้งที่ P2 กำลังทำอยู่ ถ้าใช้กฎอีกแบบที่นิยมกันคือ
        ``เสมอกันให้ตัวที่ทำอยู่ทำต่อ'' เพื่อลด context switch ผลของ case3
        จะออกมาไม่เหมือนกัน จุดนี้จึงเป็นเหตุผลที่โจทย์ต้องระบุกฎ tie-break ไว้ชัดเจน

  \item \textbf{ช่วง IDLE และประสิทธิภาพ}: case2 มีช่วง \code{[2-5]} ที่ P1 จบแล้ว
        แต่ P2 กับ P3 ยังมาไม่ถึง ในโค้ดจัดการด้วยการเพิ่ม \code{time} ทีละหนึ่ง
        แล้ววนต่อ ซึ่งตรงกับพฤติกรรมของระบบจริงที่เคอร์เนลรัน idle task
        หรือสั่งให้ CPU เข้าสู่สถานะประหยัดพลังงาน โค้ดนี้มีความซับซ้อน
        $O(T \times n)$ เมื่อ $T$ คือเวลารวมและ $n$ คือจำนวน process
        ซึ่งเพียงพอสำหรับข้อมูลระดับนี้ ถ้าต้องรับข้อมูลขนาดใหญ่จริง ๆ
        สามารถเปลี่ยนเป็นแบบ event-driven คือคำนวณเฉพาะตอนที่มี process
        มาถึงหรือทำงานจบ แล้วใช้ priority queue เก็บ ready queue
        จะลดลงเหลือ $O(n \log n)$
\end{itemize}
